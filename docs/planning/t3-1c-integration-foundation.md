# T3-1c：製品接続のデータ保持と二段階の確定

2026-09-22。[因果検証](../verification/t3-1c-causal-aggregation.md)後の続行指示に基づく接続設計。Coreに元座標の型・記述収集・文書の範囲確定を追加した。CLIからの呼び出し、`carry_enabled`の設定読込、候補生成・画素検証・因果集約・レポート接続はまだ行わない。既存の設定・実行経路はそのまま。

## 保持するデータ

| 型 | 保持する内容と責任 |
|---|---|
| `PageFlowPageKey` | 元A/Bと1以上の物理ページ番号。Canvasは不可 |
| `PageFlowBand` | 元ページ上の全幅・半開区間。開始は非負、高さは正、終端の整数あふれを拒否 |
| `PageFlowLine` | 省略していない本文、元の矩形、ベースライン。数字・大文字小文字・全角半角は区別 |
| `PageFlowPageDescriptor` | サイズ、抽出状態、行一覧、ラスタ行ごとのSHA-256と非白フラグ、全BGRのSHA-256 |
| `PageFlowDocumentDescriptor` | 選択された全元ページの記述と予算の使用量。収集未完了では作らない |
| `PageFlowCandidate` | 元／先の帯、画像検証の成否と理由。曖昧で範囲自体が未定なら帯はnull |
| `PageFlowPageProof` | ページの写像成立と、対応付けた送り端点の帯。実構造IDの発行は後段 |
| `PageFlowRangeDecision` | 全体の採否・理由・選択リンク・各ページのcandidate／baseline／unpaired |

記述データはMat、PDFハンドル、抽出語配列を保持しない。各ページの描画画像を解放した後も使える。全文の語を持ち越す代わりに、本文と座標を行単位にまとめる。元の語・ベースライン配列を変更しても保存値が変わらないことを確認する。将来の切断候補が行の外接矩形を横切る場合は保守的に見送り、必要ならそのページだけ再抽出する。

ハッシュは候補の絞り込みと再読込の整合確認に使う。**ハッシュ一致だけで画像検証済みにはしない。** 元BGR帯の全画素比較、既存比較器の安全条件、両端の実効設定の確認は別の処理として残す。非白は一チャンネルでも255未満であり、254の薄い画素を落とさない。

## 内部の予算

上限は送りを見送って通常比較を継続するための内部定数で、比較式・検出しきい値・既存PDFの入力上限を変更しない。今回の正例／多数候補／境界計測を根拠に以下を採用する。設定YAMLへ上限キーを追加しない。

| 対象 | 上限 | 超過理由 |
|---|---:|---|
| 選択した物理ページ番号 | 128（A/Bの記述は最大256） | `flow_page_limit` |
| 全選択ページの行数 | 32,768 | `flow_line_limit` |
| 保持本文のUTF-16文字数 | 2,097,152 | `flow_text_limit` |
| 記述化する元画像の累積画素数 | 536,870,912 | `flow_pixel_limit` |
| 記述データの計上量 | 64MiB | `flow_descriptor_limit` |
| 検証済み・見送りを含む全候補数 | 128 | `flow_candidate_limit` |
| 端点の証明帯数 | 256 | `flow_proof_limit` |

記述の計上量は、ページごとに `96 + 高さ×33 + 行数×96 + 本文文字数×2` バイト。33は行ハッシュ32バイトと非白フラグ1バイト。これは実RSSの上限保証ではなく、保持データに対する再現可能な予算。ランタイム・一時抽出配列・画像・辞書の余剰容量などは別に計測する。

既存の1ページ2,000行、PDF文字抽出の文字／単語数、最大辺16,000pxなども維持する。文字列の整理・連結前にも残予算を確認し、ハッシュ配列は画素数・行数・文字数・記述量を確認してから確保する。ページ数は描画前の選択計画で確認できる。画素数は今回のAPIでは渡されたラスタから確認するため、PDF描画前の割当保証ではない。

一度超えたら失敗理由を固定し、保持していた全ページを破棄する。後続の小さいページで成功へ戻さない。使用量は診断値として残すが、部分的な文書記述は返さない。候補上限超過は候補を列挙・配列化する前に見送り、先頭128件を使って一致や一意性を判断しない。将来の生成側でも129件目を見つけた時点で生成を打ち切り、文書全体を見送る。

実測ではA4・300dpiの30ページ×新旧は画素予算内、31ページ×新旧は62枚目を記述化する前に超過した。128ページという件数上限が、任意サイズの128ページを処理できる保証ではない。詳細は[計測結果](../verification/t3-1c-integration-foundation.md)。

## 二段階の確定

第一段階は文書全体の**範囲確定**。レイアウト、全候補の画像検証、すべての対応ページの写像、全端点の証明がそろった場合だけ比較面を採用する。以下は文書全体をbaselineへ戻す。

- 選択ページの証明が欠ける、重複する、別ページへ付いている。
- 帯が元ページ外、同じ側を結ぶ、物理的に隣接しない、高さや幅が合わない。
- 端点が重複・重なり、同じ内容を複数回使う。
- 候補のない証明帯、範囲の証明がない検証済み候補が残る。
- 上限、画像不一致、未検証候補、写像失敗がある。

第二段階は、第一段階で実際に採用した比較面から作った構造ID・内容クラスタに対する**因果集約**。前回検証した本文順序・原因の一意性・収支・所属・網羅性を照合する。範囲確定が成功しても、複数原因や片側ページの帯外内容で集約を見送ることがある。件数・表示状態・終了コードは承認済みの意味を維持する。

片側ページは第一段階でもunpairedのまま。その帯の確認はページ全体の検証でも、構造IDの発行でもない。第二段階へは補助帯として渡す。

## CLIへの接続順序

現在のCLIはページごとに描画・比較・保存して解放している。しかし次ページだけ待つ方式では、その先の写像失敗に対して文書全体を戻せない。画像を全文書分保持せず、先に選択範囲全体の記述・証明をそろえる。

1. `carry_enabled`がfalseなら現在の実行経路をそのまま使う。新しい収集器の作成や隣接ページの追加読取をしない。
2. 有効な場合だけ選択計画を予算検査し、元ページを逐次描画・記述化して解放する。固定部分・候補の推定は記述データで行う。
3. 候補を持つ隣接ページを逐次再読込し、元帯の全画素一致と安全条件を検証する。次に全対応ページのC/D写像を検証し、範囲確定を行う。この時点で利用者向けのページ結果はまだ書かない。
4. 確定した経路で最終比較・保存する。基準経路なら既存RowComparer、採用経路なら検証済みC/Dを使う。実構造IDと内容件数を集め、`ReportWriter.Complete`の前に因果集約を確定する。

再読込中に元画素や写像の前提が変わった場合は、候補と基準結果を混在させて保存しない。実行を失敗させ、既存の出力ワークスペースで旧結果を保護する。必要な再描画回数・ピークRSS・保存量は製品接続後に測る。今回の記述処理の速度をCLI全体の性能として扱わない。

全体補正・領域・除外・設定値は、比較面を作る段階で実ページの条件を受け渡す必要がある。元座標の証拠と全体補正後のC/Dの座標を別に保持し、raw evidenceは補正前入力から生成する。これらの接続と、既存の表示／保存／上限との組合せは今回のCore基盤だけでは受け入れない。

## 現在の到達点

追加したCore基盤を33テストと既存76実行で検証し、全1,746テスト成功。[結果](../verification/t3-1c-integration-foundation.md)を参照。既存の81製品ファイルは変更せず、Coreに3ファイルを追加した。続く[Core移行](t3-1c-core-pipeline.md)では候補生成・帯の画像検証・C/D構築・因果集約をこの型と予算へ移し、固定76実行で一連の処理を照合した。後続の[CLI接続](t3-1c-cli-integration.md)で採用条件・設定・レポートへ接続済み。全体補正の座標合成は未検証のため補正採用時は送りを見送る。複数原因の分離、数値変更を含む集約の未成立は引き継ぐ。
