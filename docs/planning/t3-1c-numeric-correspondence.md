# T3-1c 数値変更を含む行対応の設計と独立検証

2026-09-23。[複数原因の製品接続](../verification/t3-1c-multiple-cli.md)に続く計画。前半は製品を変更しない独立検証の条件を定め、後半の「製品接続の具体案」は、その検証結果を受けて承認された実装範囲を定める。

## 試す限定案

本文そのものの一致と、同じ行と推定した対応を分ける。数値の変わった行も実画素をC/Dへ残し、内容差分として判定する。同じラベルだけでは対応を認めず、次をすべて要求する。

1. 全物理ページが対応し、選択範囲の省略がない。既存の固定部・一定行間隔・本文範囲の準備が成立する。
2. 元の本文行は各側で文書全体を通して一意、共通する完全一致行の順序が同じ。数値欄を置き換えたラベルも各側で一意。
3. 同じ物理ページで、単語数・非数値トークン・非数値トークン位置が一致し、数値トークンの値だけが異なる。少なくとも二つの非数値トークンを要求する。ASCIIの符号付き整数・小数から始め、桁区切り、全角数字、文字列の一部の数字、複数行への折返しは一般化しない。
4. 直近二行が両側で完全一致する（前二行、後二行、または前後一行）。その全行と数値変更行の相対位置が同じで、同じ追加dyを支持する。数値変更行を別の数値変更行の根拠に使わない。
5. 数値変更行は同一ページ内の対応だけ。ページを跨ぐ送り帯へ緩い一致を導入しない。元帯のBGR全画素一致と置換検証はそのまま必須とする。
6. 数値変更行の全幅・全高をCの対応する区間へ残し、Dで元画素を保持する。構造帯として除去しない。変更の元矩形・C/Dの矩形・内容クラスタを独立に照合する。
7. 移動量・支持帯・支持インク・一意性・改善率は既存条件のまま。数値変更行を、完全一致する本文の支持行へ昇格させない。範囲が作れても採用が不成立なら文書全体を見送る。
8. 因果集約は数値変更の対応IDを使って実構造・移動・収支を検証するが、内容クラスタを減らさない。一つでも未説明の成分・構造があれば全グループを取り消す。

独立ツール内の一時的な対応ID・文字ラベル差替えと、元本文を記録する。ラスタの数値の塗り潰し、比較しきい値の緩和、差分マスクの消去は行わない。実CLIの従来結果と診断結果を区別する。

## 固定する検証

既存の `flow-number-change` と複数原因の末尾数値変更を再利用する。数値変更の位置（先頭・中間・末尾）、符号・小数点・桁数、複数の数値欄、A/B逆転を合成PDFで確認する。反復ラベル、非数値ラベル変更、隣接する数値変更、支持不足、行の入替え、送り帯そのものの変更を対照にし、曖昧な入力は従来比較を維持する。

生成時の正解行を推定器へ渡さない。対応・根拠行の欠落／重複／順序／位置、選択範囲を変更する監査を行い、Pythonの編集列・元画像からのC/D再構成・既存参照マスクで照合する。少なくとも一つの成立例だけで、既存の数値変更ケース全体を合格にしない。

O/Gの合成、除外・領域、片側ページ、資源上限・保存・公開出力との製品接続は後続。今回の証拠をWindows・実帳票・A4未成立9条件・大規模性能・ブラウザー／JavaScript保留の受け入れへ流用しない。

## 独立検証で確認した境界

[検証結果](../verification/t3-1c-numeric-correspondence.md)の25ケース・50方向では、写像成立26、既存の採用条件まで成立24、見送り26となった。末尾 `555→556` は内容差分40画素・1クラスタを残して候補内訳6→2、離れた二つの数値変更は7→3、別々のページ群の二原因と数値変更は11→3。符号・桁数・複数数値欄で内容クラスタが二つになった場合も二つを維持する。

特に、対応IDを元本文の代わりに完全一致の支持へ使うと、支持不足を誤って通す入力が両方向で成立した。変更行の近くにある二つの一致行の文字・罫線を薄くした対照では、元本文による支持は `insufficient_support / support_ink`、IDを本文扱いした評価だけが採用となる。写像の成立と支持の成立は別であり、この反例を後続の固定回帰条件とする。

## 製品接続の具体案

承認された製品接続は上記の限定条件を対象とする。[接続結果と検証](../verification/t3-1c-numeric-cli.md)を参照。新たな数値の許容誤差や比較モードは設けず、既存の `rows.carry_enabled` の有効範囲で扱う。送り無効時の動作を維持する。

1. **行IDと元本文を別の型で持つ。** 元の文字・矩形・基線を不変に保ち、同一ページの数値対応に、両端の行参照・数値トークン位置・完全一致する二つの根拠行を付ける。Core内へ診断用の文字差替え・反射処理を移植しない。文字一致と数値変更の対応を区別する。
2. **写像と非送りの証明へ限定して行IDを使う。** 元の完全一致による送り候補・全画素の元帯検証は維持する。数値対応は同一ページ内だけとし、候補末尾の対応・範囲構築・同一ページ対応済みの非送り証明へ使用する。元候補IDと不成立理由を残し、数値変更行を送り帯にしたり、構造帯としてCから省いたりしない。
3. **採用評価は元本文だけで支持を作る。** 数値対応は、支持行数・支持インク・単語一致率・曖昧さの解消へ加算しない。現行の列条件・画素再探索・改善率を維持する。薄い支持行の固定対照を両方向で拒否し、部分的に採用したページや集約グループを残さない。
4. **因果集約では実構造と内容クラスタを保持する。** 行IDから挿入／削除・送り収支・独立成分を照合し、内容クラスタの数・矩形・元画素は全件残す。単一原因と別成分の複数原因に限り、同じ成分の複数原因・片側ページとの新たな組合せは追加しない。
5. **補正・設定・予算へ明示的に接続する。** 縦補正時はGで行対応を証明し、元のO矩形へ一度だけ戻す。対応と根拠行の欠落／重複／別文書流用を拒否し、既存の64MiB記述予算へ追加分を計上する。上限超過、明示的な選択、除外で根拠行を失う場合は従来比較へ戻す。既存の除外／領域、入力変更、再読込、保存失敗の保護を維持する。
6. **出力に推定根拠を残す。** JSON／HTMLには「数値変更を含む行対応」であること、両側の元本文・O矩形・根拠行を記録し、文字や画像が等しいと表示しない。ページ別内訳と集約後件数を分け、内容クラスタ・未比較・終了コードを維持する。raw evidenceはOの元画像から作り、推定行ID・採否・比較設定を参照させない。

受け入れは今回の固定50方向と既存76条件・複数原因28方向・縦補正を実CLIで再検証し、無効時の従来出力、見送り時の通常比較への復帰、元A/B・raw overlay、C/Dの元画素と数値変更クラスタを照合する。対応IDや根拠行の改変、予算境界、除外／領域、compare-dir、入力変更・保存失敗を追加し、全テストとビルドを通す。時間・RSSは接続後に計測する。今回の独立ツールの成功をこれらの製品受け入れに代用しない。
