# T3-1c Coreの候補・画像検証・表示投影・因果集約

2026-09-22。[接続基盤](t3-1c-integration-foundation.md)に続く実装範囲。Coreだけで元画像の記述から候補、帯の検証、全選択ページの範囲確定、C/D比較、実構造IDによる集約までを扱う。本書はCore移行時点の契約。後続の[CLI接続](t3-1c-cli-integration.md)で設定・レポート接続と採用条件を追加した。[検証結果](../verification/t3-1c-core-pipeline.md)を参照。

## 処理と所有権

| 処理 | 入出力・条件 |
|---|---|
| `PageFlowInference.Find` | `PageFlowDocumentDescriptor`から固定部・等間隔本文・隣接物理ページへの候補を推定。画像や正解座標は受け取らない |
| `PageFlowBandVerifier.Verify` | 再読込した元A/Bの寸法・BGR SHA256を確認し、全幅の帯を画素で直接照合。完全一致後に各元ページへ置換し、両端・両順序で生差分0を検査 |
| `PageFlowSurface.Create` | ページ内の完全一致本文と検証済み送り帯から構造帯を組み、既存`RowComparisonSurface`でC/Dの被覆・白帯・近傍を検証 |
| `PageFlowPlan.Prepare` | 候補の検証、重複端点の拒否、全ページの写像検証、範囲確定を順に実行。返すのは画像を含まない計画 |
| `PageFlowPlan.Compare` | 文書全体の範囲が成立した対応ページだけを比較。元画像のハッシュを再確認し、Cの比較とDへのクラスタ・構造投影を返す |
| `PageFlowAggregation.Evaluate` | 本文順序、送り行の範囲、実構造ID、各ページの収支、全構造の所属を確認し、連続した単一の挿入／削除原因だけを集約 |

`Prepare`の読込コールバックは新しい所有権を持つMatを返し、Coreが逐次解放する。候補検証では隣接2画像、写像検証では同一ページのA/Bだけを読み込む。文書全体のMatは保持しない。帯の置換画像や比較マスクは各検証内で解放する。

最終比較の入力A/Bは呼び出し側の所有。`PageFlowComparison`はCの画像2枚、内容比較、Dの投影を所有し、Disposeで解放する。比較時のページ番号を保持して、集約用の構造参照にはその番号と実際の構造IDを使用する。Coreにはファイル・PDF・コンソール処理を置かない。

## 証明と見送り

- ハッシュは再読込の同一性確認と固定部の絞り込みに使い、送り帯の完全一致を代用しない。BGRの255→254一画素も帯の不一致として見送る。
- 帯検証では通常設定・厳密設定・許容移動0.30mmの設定、および実際の比較領域のDiff設定を重複なく使う。領域によるマスクや除外は証明に使わない。既定では2端点×2順序×3設定の12比較となる。
- 帯は一致しても、後半ページの写像が作れなければ全対応ページを基準経路へ戻す。`Compare`はその計画から成功ページだけを利用する操作も拒否する。
- 元画像が記述収集後や範囲確定後に変わった場合は`flow_original_changed`を含む処理エラーにする。CLI接続時は既存の出力ワークスペースで旧結果を保護する必要がある。
- 候補が128件を超えた場合は途中の候補を返さず、画像の再読込前に文書全体を見送る。記述・本文の上限は接続基盤から維持する。
- 切断判定は語配列ではなく保存した行の外接矩形で行う。行の矩形が境界をまたぐ場合は保守的に見送る。固定部のキーは本文と丸めた座標の組で、区切り文字やカルチャーによる連結キーの衝突を避ける。
- 因果の根拠不足では未集約件数を維持する。内容クラスタは集約しない。片側ページの網羅性は常にfalseで、補助帯から構造IDや差分件数を作らない。無効時の集約件数・網羅性はnull。

## Core移行時の設定受け渡しと後続条件

候補探索は実際のDPIと`RowOptions.MaxShiftMm`／`MinSupportBands`を参照する。`rows.enabled=false`の計画では画像再読込を行わない。ただし製品でcarry無効なら、計画や記述収集自体を呼ばないことが必要になる。

C/Dの安全近傍と実比較には`ComparisonParameters`を渡す。領域優先順位と除外をDで決めてCへ写す既存経路を使用し、構造投影にも同じ設定を渡す。設定のリストは準備時に複製し、呼び出し側の配列変更で最終比較の条件を変えない。

これは候補・範囲の成立を扱う段階であり、既存のページ内行整列の採用条件をすべて代替するものではない。`MaxSegments`、支持インク面積、改善率、スコア差などのRowOptionsと送り経路の採用条件の対応付けはCLI接続前に整える。今回の固定入力の成立を、その設定の網羅確認として扱わない。

また、全体補正済み画像と元座標の合成、アンカー除外の解決、PDF・画像混在やサイズ不一致、選択ページ・片側ページの最終保存、件数・網羅性・終了コードの伝搬は未接続。比較器から独立したraw evidenceは従来どおり補正前入力から生成する。

次は上記の採用条件・全体補正との座標契約を接続し、`rows.carry_enabled`、CLIの事前検証と最終比較、JSON/HTML出力を実装する。複数原因の分離、数値変更を含む因果集約、WindowsとCLI全工程の性能・保存失敗時の検証は引き続き未完了。

CLI接続後は `PrepareForPages` でページごとの実効条件を固定し、帯の両端のDiff条件を検査する。`PageFlowAdoption` が共通の `RowGroupValidator` と `RowSupport` を使って採用条件を確認する。元帯検証後の範囲失敗は、画像検証自体の成功と別に報告する。移行時点の残件の解消範囲は[CLI接続の記録](../verification/t3-1c-cli-integration.md)を参照。
