# T3-1c：ページ送りの対応付けと文書レベルの集約

2026-09-22。[TASKSのT3-1c](../TASKS.md)の仕様案。判断案はユーザーの「OKです。進めてください。」で承認済み。状態は**限定入力についてCoreから設定・CLI・JSON／HTML・compare-dirまで接続済み。全体補正を採用した文書は送りを見送る**。[CLI接続の条件](t3-1c-cli-integration.md)を参照。[接続設計と上限](t3-1c-integration-foundation.md)を参照。複数原因の分離と文字変更を含む集約は未成立。T3-1bのブラウザー確認の一部は[ユーザー指示で保留](../verification/t3-1b-browser-handoff.md)し、この設計へ進む。保留の解消を着手条件に戻さない。

最初の事前検証ではType3の20PDFを固定し、177比較のC#／Python参照一致と現行CLI40実行を確認した。正常な送り帯は単独なら完全一致するが、元画像の周辺を直接比べると帯内に4〜8pxの差分が残った。[最初の観測結果](../verification/t3-1c-page-flow-probe.md)を参照。

続行指示を受けた追加検証では、元ページの候補帯だけを相手の元画素で置き換え、元ページ全体を両端・両順序で比較した。750比較がC#／Pythonで一致し、共通面174テストも再確認。許容付きの置換検証だけでは、境界をまたぐ薄色変更を二分して見逃すため不採用。**帯の全画素一致を必要条件とする限定案**なら、R10／R11／連鎖の正解帯で境界の偽差分を解消でき、変更のある帯は未確定に残せた。[境界の補足案](t3-1c-context-verification.md)と[追加検証](../verification/t3-1c-context-verification.md)を参照。自動候補・構造認定・集約・製品接続は未完了。

## 目的と承認済みの判断

1行の挿入・削除から複数ページへ連鎖した送りを、画像で確かめたうえで関連付ける。ページごとの相違と根拠を残し、文書では同じ原因をまとめて表示する。

| 判断 | 承認内容 |
|---|---|
| 送りだけの文書 | 相違のまま。終了コード1を維持する |
| 件数 | `summary.clusters`・`structural_change_count`・`difference_count`は未集約の意味を維持する。別項目`aggregated_difference_count`を追加する |
| 有効化 | `rows.carry_enabled: false`を追加し、明示した場合だけ評価する。trueには`rows.enabled: true`が必要。既存のrows有効設定だけで新処理を始めない |
| 確信できない対応 | 候補／見送り理由を残し、相違を消さず、集約しない |
| 新しい片側ページ | 内容を確認できた範囲を注記する。`only_in_a`／`only_in_b`、終了コード、未比較を表す既存の網羅性は維持する |

上記は2026-09-22に承認済み。以下の境界処理はまず独立した事前検証で確かめる。比較式を変更したり、現在の検出期待を緩めたりしない。

## 既存コードから分かった制約

- `ComparisonRunner`はページを逐次比較し、画像・行整列結果を`ReportWriter.AddComparedPage`へ渡して、そのページのMatを解放する。文書集約は`ReportWriter.Complete`の前に確定させる必要がある。
- `RowMatching`の行対応は内部データで、採用したLCSと未対応行の並びを文書処理へ直接渡す公開契約はない。HTMLの省略済み本文から対応を復元してはならない。
- `RowCandidateBuilder`は末尾に残る片側帯が非白なら`no_bands / edge_content`として見送る。ページ送りはまさに非白の行が端から出入りするため、現在のJSONへリンクを後付けするだけではR10を満たせると断定できない。
- 片側だけのページは`AddUnpairedPage`で保存し、行整列結果は`not_compared`。既存のクラスタと構造IDはない。送り先の帯には独立した参照が必要になる。
- 既存の総箇所数は内容クラスタ＋除外されていない構造変化。片側ページの未比較や上限省略は`difference_count_complete=false`であり、送りを確認しても既存の意味を変更できない。

このため、最初の工程はR10／R11の入力を固定し、隣接ページの根拠を使う端の帯の契約を検証することとした。上記は設計時点のコード所見。実行した現行CLIでは、固定フッターありの入力は`ambiguous / non_equivalent_safe_cuts`で見送った。詳細は[事前検証](../verification/t3-1c-page-flow-probe.md)に分けて記録する。

## 対象と有効化

- PDFテキスト層が使える、元の寸法とDPIが対応する隣接物理ページを対象とする。画像ルートはT3-1dへ残す。
- 候補の方向はAのp末尾→Bのp+1先頭、およびBのp末尾→Aのp+1先頭。1ページ以上の内容量のずれ、ページ自体の入れ替え、途中ページ全体の挿入、独立した列ごとの送りは対象外。
- `--pages`は実際に選んだ隣接ページだけを評価する。pとp+2を隣接扱いせず、未選択ページを追加で解析・描画しない。途中で切れた連鎖は部分的な確認として記録する。
- `rows.carry_enabled`はbool。共通YAMLと帳票別YAMLのスカラー継承、未知キー・型の検査、実効設定のJSON／HTML表示を既存のrowsと揃える。専用CLIフラグは追加しない。`--no-regions`はこの値を変えない。
- 無効時は隣接ページの追加読取・文字抽出・画像検証・保存を行わない。完全一致の既存経路を維持する。

## 候補と画像検証

1. 元ページの語・矩形・ベースラインを使う。行は既存の`TextLineLayout`で作り、照合用の文字列には既存の空白・制御文字整理だけを適用する。数字・連番・全角半角・大文字小文字を同一化しない。
2. ページ内の支持された対応で挟まれた本文領域を使い、端に続く未対応行列のsuffix／prefixから候補を作る。共通のヘッダー／フッターを対応済みの固定部分として扱い、利用者に範囲指定を要求しない。本文と固定部分を区別できない場合は曖昧として見送る。
3. 文字列の一致は候補の根拠に限定する。同じ文字列の繰り返しで複数の物理帯が対応する場合、探索の先頭を採用しない。往復で同じ帯の組になる一対一の対応を要求し、1帯を複数リンクに使わない。
4. 候補帯は元の画素から取得する。内容・罫線・薄い塗りを保持し、文字だけを抜いた画像や表示面Dの白い詰め物は検証に使わない。全体補正は座標の対応に一度だけ反映し、補間拡縮しない。
5. 5章の既存比較器で検証する。ノイズ除去後のクラスタ数0だけでは確定せず、生差分0を必要条件とする。除外して一致させた結果を「内容変更なし」の根拠にはしない。帯の両端に関わる実効diffで検証し、どちらの設定でも生差分0であることを記録する。
6. 切り出しの端で近傍・二段目のgroupを切ることが検証結果へ影響しないよう、必要な元画像の周辺と座標を保持する。安全な比較範囲を作れなければ`unsafe_boundary`として見送る。周辺の捨て方や白い余白の追加で差分を消す方式は採用しない。ここは事前検証の必須項目。
7. 検証に通った組だけを`carried`とする。文字は同じでも画素の色・線・記号が異なるケース、文字の変更、曖昧な対応、切断不可では従来の相違を残す。部分一致を根拠に帯全体をまとめない。

境界処理の初期案は[補足仕様](t3-1c-context-verification.md)を参照。生差分0だけを十分条件にはせず、全画素一致しない帯は送りを確定しない。通常比較で吸収される微小移動も送り未確定になる制約がある。通常比較の式やしきい値は維持する。

端にある非白帯をページ内の内容比較から外す拡張は、送り検証に通り、T3-1bの内容保存・近傍・置換の安全条件も成立する場合だけ、`carry_enabled`の経路に導入する。単に`edge_content`の検査を外さない。隣接ページの検証が不成立なら現在のページ比較へ戻す。

## 因果の連鎖と件数

`carried`は「この2帯の内容が一致した」という根拠であり、複数の送りが同じ原因であることを単独で保証しない。文書集約には、原因の挿入／削除が一意、送りの順序と帯数の収支が対応、途中の独立した変更が混ざらないことも必要とする。

- 集約グループは原因の構造変化、対応するブロック移動、検証済み送りの端点を参照する。既存の構造参照は`{page, structural_change_id}`で持ち、ページ内の`related_cluster_ids`を転用しない。
- 内容クラスタは集約によって削除・合併しない。送りと同時に数値変更が1件ある場合、送り連鎖1件＋内容変更1件として残す。
- 同じ構造変化を複数グループに数えない。1つの構造帯が複数原因へまたがり分離を証明できない場合は集約を見送る。
- 未集約総数をU、確定した各グループに属する既存の非除外構造ID数をnとすると、集約後は `U - Σ(n - 1)`。画像検証用の補助帯を新しい相違として加算しない。
- 集約できない送り候補や曖昧な原因は未集約のまま残す。チェーンの途中で未確認箇所がある場合、全範囲を「検証済み」と表示しない。
- `aggregated_difference_count_complete`を別に持つ。既存の網羅性がfalseならtrueへ引き上げず、未比較・選択範囲・上限等の残る範囲を併記する。無効時の集約後件数はnullとし、0件と混同しない。
- CLI／HTML／compare-dirでは、例えば「集約後1箇所（ページ別内訳N箇所）」と両方の意味を明記する。`summary.clusters`・構造件数・既存総数・ページ数・状態・終了コードは各段階の契約を維持する。

## 片側だけの新しいページ

元ページ上の送り先帯を、ページ番号・側・矩形を持つ独立した補助帯として保存する。既存の構造IDがないため、架空のIDで`row_alignment.structural_changes`へ参照させない。文書の送りリンクから補助帯を参照し、既存構造を指せる端点には併せてその参照を付ける。

「送り帯と固定部分だけ」という注記には、新しいページの全非白内容が検証済み送り帯と確認済み固定部分に含まれることを必要とする。残りを白と決めつけたり、インク閾値未満の薄い内容を捨てたりしない。

固定部分は対応ページで位置・文字・画像の一致を確かめたものだけを使う。本文の反復行を固定部分と誤認する、ページ番号の変化を勝手に除外する、根拠が1ページしかない場合にレイアウトを推定して確定する、といった処理は行わない。確認不能なら送り帯の対応だけを注記し、ページ全体は未検証とする。R11には固定部分の根拠を取れる2→3ページの正例と、1→2ページで固定部分の根拠が不足する負例を用意する。

## 出力と処理の境界

追加出力は文書の`page_flow`にまとめ、評価状態・理由・帯の参照・検証したリンク・集約グループ・片側ページの確認範囲を区別する。元座標は`original_top_left`とページ番号・側を必ず持ち、必要な表示面Dへの参照も別に保持する。既存の構造の`kind`やIDを`carried`へ置き換えない。

HTMLは文書要約、送り元／先への相互リンク、ページ別内訳の折り畳み、元帯の確認画像を追加する。JavaScriptがなくても要約・内訳・リンクを読めること。画像検証失敗と未実施を表示上も分ける。補正前のraw evidenceと既存のページ／切り出し画像は、それぞれ承認済みの意味を維持する。

PDFiumの逐次描画とページごとの解放を維持し、全文書分のMatを保持しない。文書全体の見送りを可能にするため、選択範囲全体の記述・帯検証・写像を確定してから利用者向けの結果を保存する。次ページだけ待つ方式ではその先の失敗に戻せないため、[接続設計](t3-1c-integration-foundation.md)では段階ごとの再読込を使う。画像の追加読み取り・最大RSS・保存量は実測し、例外時は持ち越した資源も解放して既存の出力ワークスペースで旧結果を保護する。

既存の文字数・行数・仮説数の制限は維持する。候補の組合せ探索を打ち切って一致や一意性の根拠にしない。[接続基盤の計測](../verification/t3-1c-integration-foundation.md)に基づき、選択128物理ページ・計32,768行・本文2,097,152 UTF-16文字・記述化512Mi画素・記述計上64MiB・候補128件を内部上限とした。上限超過は文書全体の送り見送りとし、通常比較を維持する。記述計上量は実RSSの保証値ではない。

## 実装前の事前検証

1. 再現可能な埋め込み文字層付きの複数ページPDFでR10／R11を作る。既存のSkiaSharpによる複数ページ生成と、自作Type3フォントの座標が固定された入力の両方を使い、表示差と文字層の差を区別する。OSフォントや機密帳票は使わない。
2. 現在のT3-1bの出力を先に保存し、端の非白帯・先頭アンカー・固定フッターでどこが見送られるかを記録する。R10／R11を既存実装で検証済みとは扱わない。
3. 独立した試行で、文字候補→元画像の比較→端の帯の内容保存→C/Dの近傍→元座標を確認する。共通面の既存174条件と境界変更の期待を維持できなければ製品へ接続しない。
4. R10／R11・連鎖の収支・曖昧性・集約の所属が成立した後、候補上限とデータ型を固定し、Core→CLI→JSON／HTML／compare-dirの順で実装する。

## 受け入れケース

| ケース | 必須の期待 |
|---|---|
| R10・2ページ | 原因の挿入とページ内移動を保持し、末尾→次ページ先頭の送り1組を画像検証。内容変更なし。文書では原因と連鎖を1グループにする |
| R11・2→3ページ | 合計帯の送り先を新しい片側ページ上で確認する。固定部分以外に内容がない正例を注記。only_in_bと終了コード1は維持 |
| A/B交換 | 削除・繰り上がりへ対称に変わり、件数・参照関係・元座標が対応する |
| 3ページ以上の連鎖 | 1原因の検証済み連鎖を集約後1件にする。全ページの未集約内訳を保存する |
| 2つの独立した原因 | まとめて1件にしない。所属が曖昧なら集約を見送る |
| 送り＋数値／小数点／マイナス／色／罫線変更 | 変更帯をcarriedにせず、変更を残す。同じ文字列で画素だけ違う負例も含む |
| 反復行・同名見出し・固定フッター | 帯の一対一対応と固定部分の根拠を確認。曖昧なリンクを確定しない |
| 境界・薄色・途中の置換 | 帯端の変更を切り捨てず、非白の余白を保持。5章の判定・既存の安全網を維持 |
| 領域・除外・全体補正 | 二重補正なし。除外で消えた差を送りの同一性の根拠にしない。両端の実効設定と元座標を保存 |
| ページ選択・欠落・抽出失敗・上限 | 未確認の隣接ページを読み足さない。見送り理由と部分的な網羅性を記録 |
| 無効時・対象外 | T3-1bの固定出力に対し、承認した設定・新規項目以外のJSON／HTML／PNG／終了コードが一致 |
| raw evidence | 有効化・採用・見送り・除外・文書集約で元画像と確認用オーバーレイが全バイト一致 |

実CLIで複数ページPDF、`--pages`、`--no-html`、compare-dir、保存失敗時の旧結果保持を確認する。A4・300dpiの2／3ページ、完全一致、送り、見送り、多数候補を計測し、時間・最大RSS・追加保存量を報告する。新しいブラウザー表示とWindows配布物の静的検証はT3-1cの独立した受け入れとし、T3-1bの未確認を自動的に解消した扱いにしない。

## 停止条件と今回の範囲

続行指示を受け、[自動候補と構造帯の方針](t3-1c-candidate-inference.md)を独立ツールで検証した。32PDF・36実行・480参照比較が一致し、R10／R11／連鎖の候補を正解座標なしで推定できた。一部の変形入力では画像帯が一致しても本文端の非白1pxにより構造写像が作れず、範囲対応は未成立として残した。[結果と再開位置](../verification/t3-1c-candidate-inference.md)を参照。次は別系統のPDF、固定部分・描画端の曖昧さ、写像の部分失敗を含む契約の確認。製品コード、比較式、検出期待、依存、公開済みv0.1.4は変更していない。因果集約・構造ID・製品接続は未完了。

その後、[Skiaと文書単位の確定](t3-1c-document-gate.md)を検証した。合計70実行・878参照比較が一致し、行内座標を共通にしたSkia入力で送り帯とCが成立。絶対座標描画で生じる罫線の実差は検出したまま見送る。部分写像失敗は文書全体を基準比較へ戻し、210順序条件・160根拠欠落条件でも部分採用を残さなかった。[最新結果](../verification/t3-1c-skia-document-gate.md)を参照。次は成立した入力で因果・収支・複数原因の集約を独立検証する。

実装には[TASKSの共通条件](../TASKS.md)の「着手時に `docs/planning/` に仕様案を作り、各タスクの『着手前に確認する判断』の承認を得てから実装する」を適用する。上表の判断と事前検証への着手は承認済み。事前検証で差分の見逃し、R10／R11の不成立、式の変更が必要なことが判明した場合は、期待やしきい値を変えずに結果を報告する。
