# T3-1c 同じ送り連鎖にある複数原因の独立検証

2026-09-23。数値行対応の製品接続後の続行指示に基づく設計・独立検証。製品の集約・画像比較・設定・出力は変更しない。

## 数える単位

同じ連鎖の二挿入では、後半の移動は二原因の累積変位になる。実構造IDを原因ごとに複製せず、連結成分が原因の配列と実構造の集合を一つずつ持つ案を検証する。各移動構造には寄与する原因の参照集合と合計変位を記録する。送り帯も一度だけ数え、原因ごとに画素を分割しない。因果関係は行順序と変位を説明するもので、業務上の変更意図を推定するものではない。

成分の実構造数をn、連続した挿入／削除帯の数をk、元のページ別内訳をUとすると、集約後は `U - Σ(n - k)`。内容クラスタを減らさず、網羅性を引き上げない。隣接する追加行は一つの連続帯として扱い、文字数・行数から原因を増やさない。

## 今回試す限定条件

- 全物理ページが対応し、文書ゲートと全ページの元本文による採用評価が成功している。選択範囲の省略、未検証リンク、除外済み構造を認めない。
- 元本文が両側で一意、共通行の順序が同じ。数値対応IDの取り扱いはこの段階では一般化せず、本文が完全一致する対照で因果の検証を分離する。
- 検証済みの隣接リンクで成分を作る。共通行がリンクのない境界を跨がず、送りのないページは本文・配置が等しく構造なし。一つでも未説明の成分があれば文書全体の集約を取り消す。
- 成分内は同じ符号の挿入だけ、または削除だけ。本文の行間隔・高さ・開始位置が両側で等しく、最終ページより前の行数は両側同数。異符号の相殺、原因帯のページ跨ぎ、途中ページの容量変更は別検証とする。
- 共通行の間にある連続した差し込み帯を列挙し、それぞれが同じページの実挿入／削除構造一つと完全一致する。送り端点と原因帯が一つの構造へ混ざる場合、実IDを分割して救済しない。
- 同一ページの移動構造に含まれる全行で、直前までの原因集合が同じであることを要求する。符号付き原因高さの合計と実変位が一致し、移動した共通行を過不足なく説明する。
- 送りの全行・端点を既存の元帯証明へ照合する。各境界の送り行数と高さが、その境界までに発生した原因の累積量に一致し、ページごとの `B行数 - A行数 = 原因増減 + 流入 - 流出` が成り立つ。全実構造を原因・移動・送り端点のどれか一つに割り当てる。

## 証拠と停止境界

自作Type3の二原因、同一ページ二原因、三ページ連鎖、色変更、独立成分との併存を両方向で実行する。隣接挿入は単一原因の対照にする。三原因・複数行原因は既存の最大移動量や支持条件で成立しない可能性も含めて記録し、成立させるためにしきい値を変えない。異符号、反復本文、送り帯の画素変更、原因と送り端点の境界を負例・境界例として調べる。

比較コアが実際に出したC/D・生差分・構造ID・実CLIを取得し、独立Pythonの編集列・累積量・参照マスクへ照合する。欠落・重複・位置・変位・所属・リンク方向・除外・全体ゲート・網羅性・列挙順を変更して監査する。製品の旧未集約件数と診断候補の集約件数を混同しない。

成果は成立範囲、未成立の入力と理由、製品接続の具体案まで。製品ソースのハッシュ不変を確認する。新しいJSON／HTML表現・数値対応・全体補正・除外・予算・実CLIへの接続は後続工程。同一連鎖全般、A4未成立9条件、片側ページ、Windows・実帳票・大規模性能、ブラウザー保留の受け入れにはしない。

## 独立検証の結果

[検証記録](../verification/t3-1c-shared-causes.md)。13ケース26方向のうち8方向で診断上の集約が成立した。二挿入7→2、内容色変更を残して8→3、独立原因の後ろに共有原因がある入力12→3、隣接挿入の単一原因対照5→1を各両方向で確認した。共有移動の実構造IDを複製せず、二原因の変位100pxずつが同じ構造の200pxへ寄与することを示した。

集約を見込んだ3ケース6方向は未成立。三ページ連鎖は二つ目の送りの `ambiguous_displacement`、同一ページ二原因は `text_mismatch`、共有原因の後ろに独立原因を置く入力は境界の `ambiguous_displacement` で前段を通過しない。順序を逆にした独立原因→共有原因は成立する。順序の一般化は未完了であり、失敗した期待を成立へ書き換えていない。三原因・複数行原因等の境界例も、観測した実際の見送り段階を記録した。

## 製品接続の具体案

以下は承認済みの接続方針。[製品接続検証](../verification/t3-1c-shared-cli.md)で成立範囲の実装と確認を完了した。独立検証時の未成立6方向と一般化の制限は維持する。

1. 従来の単一原因・独立成分の集約が成功した場合は、従来結果をそのまま返す。未集約で、文書ゲート・全ページの行採用が成立した入力だけを共有原因の検証へ渡す。前段の推定器・送り帯の全画素一致・支持・写像・採用条件は変更しない。
2. Coreに成分単位の証明型を追加する。原因の配列、全実構造の一意な集合、移動構造への原因参照と累積変位、送りリンクへの原因参照、ページ収支を持つ。元の構造ID・リンクIDを保持し、原因を別々のグループへ割り当てるために構造IDや帯を分割しない。
3. 既存 `groups` の単一の `cause` は維持する。複数原因成分は任意の `shared_components` としてJSON／HTMLへ追加する案とする。要素に `causes[]`、`structures[]`、`movements[]`、`links[]`、`balance[]` を持ち、原因数・ページ別内訳・集約後を表示する。単一原因成分と共有成分の両方に同じIDを所属させない。共有成分がない従来結果には新項目を出さない。
4. 文書全体の実構造が、単一原因群または共有成分のどちらかへ一度ずつ所属した後にだけ採用する。内容クラスタを維持し、`U - Σ(n - k)` を適用する。一つでも成分・構造が未説明なら、成功した成分も含めてすべて取り消す。網羅性・終了コード・raw evidenceを維持する。
5. 今回の独立モデルは完全一致本文を使った。製品の数値対応IDを扱う場合は元本文と混同せず、既存の型付き証明だけを使用する。数値行を完全一致支持や送り帯の証明に昇格させない。数値対応と共有原因の組合せ、O/Gの縦補正、除外・領域は接続時の追加受け入れ条件とし、この事前検証で合格にしない。
6. 原因参照の数が構造数と原因数の積になり得るため、配列を確保する前に保持量を既存64MiB記述予算へ計上する。本文・画像の複製は避け、ページ・行・候補の既存上限を維持する。予算のちょうど上限／1B超過、全体取り消しを検証し、具体的な計上式をSPECへ記録する。
7. 固定26方向と既存104集約入力を製品へ接続して再検証する。数値行対応50方向、縦補正、明示ページ選択、片側ページ、除外・領域、上限、compare-dir、入力変更・保存失敗、JSON／HTML参照、raw画像を確認する。接続前後の比較で、今回の対象以外の既存採否・件数・出力を維持する。全テストと製品CLIの時間・RSS・描画回数を測定する。

未成立6方向を救済する候補推定の拡張、異符号の相殺、原因帯のページ跨ぎ、途中ページの容量変更、同一構造に混ざった原因・端点の分割は接続範囲に含めない。
