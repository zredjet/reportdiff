## 評価手順

1. 入力と人の期待値、基準コミット、実行環境を記録する。A/B は同じマシンの同じ実行で読み込み・描画し、処理中に入力を変更しない。
2. 既定値で初回比較する。PDF は既定 300dpi。画像の DPI が異なる場合は作成時の DPI を設定し、混在入力では dpi と image_dpi をそろえる。未確認の生成 DPI を推測して設定しない。
3. 一覧と個別レポートを、期待変更・ページ・位置に対応させて確認する。クラスタ数をそのまま業務上の変更数とみなさない。検出すべき変更の見逃し、無視すべき差の誤検出、指定外の差、未判定を理由とともに記録する。終了コード 0 だけで合格にしない。
4. フォント警告、サイズ差、吸収・除外・ノイズ・上限超過、全体補正の適用有無も確認する。既知の限界は [SPEC 5.6](../SPEC.md#56-既知の限界仕様)と照合し、無断で限界の定義を変えない。片側のみのファイルは存在差分で、内容は未検査。
5. 調整が必要なら、まず既存の帳票別 YAML で表現できるか調べる。変更キーと理由、改善する例、検出力を落とす可能性のある例を示す。初回結果を保持し、設定・出力先を分けて同じ入力へ適用する。複数の変更をまとめて原因不明にしない。
6. 原因を再現する必要がある場合、実帳票の切り出しではなく、図形・架空値等で独立した合成ケースを作る。新しいケースは問題の再現と修正前後の差を確認し、既存の検出必須／無視必須を維持する。
7. 帳票別設定での改善、変更不要、共通仕様の変更が必要、未解決の限界を分けて報告する。共通式・既定値や未定義の挙動の変更は、根拠と選択肢を提示して確認後に行う。

初回比較のコマンド（リポジトリルートで実行。帳票と期待値の準備後）：

```bash
# Release の実行物を先に作り、ビルド時間を比較の計測に含めない。
dotnet build -c Release
dotnet src/ReportDiff.Cli/bin/Release/net10.0/reportdiff.dll compare-dir samples/private/t2-7/inputs/A samples/private/t2-7/inputs/B --out samples/private/t2-7/results/baseline-001 --config samples/private/t2-7/settings/baseline.yaml --save-all-pages
```

既定値を使う `baseline.yaml` の内容は、コメントと `{}` のみ。明示 profile、除外、全体補正は必要性を確認してから別条件として評価する。画像 DPI の設定が必要なら、初回設定へ記録したうえで実行する。現在は空の入力フォルダしかないため、上の実帳票比較はまだ実行していない。

単一対のファイル名が異なる場合は既存の `compare A B --out ... --config ... --save-all-pages` を使える。フォルダ比較で名称を推測して対応させない。

## 時間とメモリ

既存の測定と同様、入力・DPI・ページ数・設定・OS を固定し、予備 1 回の後に 3 回を別プロセスで計測して中央値を記録する。各回に異なる出力先を使う。これは測定手順であり、速度の合格しきい値を新設するものではない。大きな帳票で反復が困難なら、実施回数と理由を明示する。

起動・読み込み・PDF 描画・比較・画像／JSON／HTML 保存を含む経過時間を記録し、ビルドや人の確認時間は分ける。macOS では `/usr/bin/time -l` による最大 RSS（bytes）を使用できる。Windows の最大メモリはその環境の計測器と単位を併記し、取得不能なら未測定とする。managed allocation を最大 RSS の代わりにしない。
