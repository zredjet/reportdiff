# 末尾の片側ページへ続く共有原因の段階別診断

2026-09-26。独立成分の限定接続に続く検討。製品の式・しきい値・支持条件・採否・集約器と既存PDFを保持し、診断ツールと別合成入力で未成立段階を調べる。

対象は補正・選択・領域・数値対応なし、300dpi／normal、一意な全文、規則的な行間隔、末尾1枚だけが片側の文書。同じ連鎖内の同符号の二原因をA/B両方向で調べる。既存 `shared-unpaired` のPDFをバイト不変の対照にし、単一R11も維持する。

第2原因を元本文の位置6〜10へ移した別入力と、3→4ページ連鎖、内容色変更を使い、候補の変位、跨ぐ全行、元帯の全画素一致、局所構造帯の前後支持、C/D作成、各ページの採用、片側残余、実構造と原因集約を個別に記録する。位置7の旧入力は現時点で未成立であり、位置8に期待する成立と混同しない。

診断候補は、文書全体の本文一意性・共通順序と、実際に境界を跨ぐ全文から末尾／先頭の完全な行帯を求める。元の最大変位と最低支持数を要求し、送り帯そのものを支持へ加算しない。既存候補で曖昧な境界も診断するが、製品の制約は解除しない。全境界が実際の跨ぎで連結する一連鎖だけを扱い、非送り候補の削除や独立群の追加一般化は行わない。

局所支持・C/D作成は製品の既存関数を使う。両側から帯を切る `unanchored_join` や支持不足が残ればその段階で未成立とする。診断が成立したときだけ、同符号の原因列・累積変位・送り高・全実構造の一意な所属・ページ別収支を独立モデルで検証する。片側の送り先は補助帯とし、架空の構造IDを作らない。全非白残余0、内容件数保持、両方の網羅性falseを要求する。

正例候補は位置8、3→4連鎖、内容色変更。位置6／9／10の支持不足、送り帯変更、帯外の濃淡・BGR254、固定部変更、反復本文、送り行自体の数値変更は見送りを要求する。成立しない正例は期待を弱めず未成立として残す。破損した行・リンク・構造・片側被覆の証拠は拒否し、列挙順と内容追加に対して結果を監査する。

Pythonで元画像からC/Dと残余を再構成し、参照比較器の生差分マスク・投影・編集列を照合する。実CLIの有効／無効出力・raw evidenceも別に記録する。診断結果は製品出力へ混ぜない。成立した場合は証拠結合・予算・補助端点の出力・設定・保存と互換を含む具体的な接続案をまとめるところまでとする。

Windows・実帳票・大規模性能・画面サイズ／JavaScript、A4用紙の未成立9条件・薄色1px線2方向は保留のまま。製品接続とT3-1c全体の完了を本診断の成果に含めない。

## 診断後の接続候補

[診断結果](../verification/t3-1c-unpaired-shared-diagnosis.md)では、第2原因の前後に2行ずつ支持がある別入力6方向が成立した。2→3ページは8→2、3→4ページは11→2、実PDFの濃淡変更1,390px・内容1件を残して9→3。旧入力の2方向は前側支持1行で未成立のまま。こちらを正例から外して合格とはしない。

選択肢は、成立6方向に限定して製品へ接続する案と、旧入力の局所支持を別契約で先に設計する案。後者には支持の新しい根拠が必要なため、**既存の局所支持と比較面をそのまま使える6方向の限定接続を推奨する**。この限定接続は利用者の「OKです。進めてください。」で承認済み。

接続範囲は末尾1枚、対応ページ2枚以上、各側が1から連続し明示的なページ選択なし、300dpi／normal相当、補正・数値対応・除外・領域なし。同符号の原因が同じ連鎖にあり、全対応ページの既存支持・改善率が成立する場合だけとする。既存の単一R11・独立成分の成功を先に返す。

1. 曖昧候補の再検証を、文書・元候補ID・レイアウト・実効設定へ結合した末尾ページの証拠に限定する。実際に跨ぐ全文と完全な末尾／先頭帯、既存の適格変位を要求する。単に最大変位を選ばず、旧候補IDを維持する。
2. 共有原因の集約は、全対応ページの実構造と末尾の片側本文を一つの連鎖で照合する。原因・移動・送りの寄与・累積高・収支を維持する。実端点の構造参照は一度だけ所属させ、片側送り先には補助帯を使う。未比較や網羅性falseを解除しない。
3. JSON／HTMLでは、既存の共有原因と送りリンクに補助端点の元ページ・側・帯・画像を添える。片側ページへ架空の構造IDを作らず、件数へ足さない。出力形式と元候補IDの対応を仕様化してから実装する。
4. 候補再検証・共有成分・補助参照の作業／結果を確保前に同じ64MiBの残りへ計上する。元文書・候補・設定の差し替え、上限ちょうど／1B不足、全グループ取消、再試行を検査する。診断用の反射や裸のDTOを製品の証拠として転用しない。
5. 固定28方向を保持し、追加の期待差は6方向だけとする。既存の末尾独立原因32方向・全ページ対応の共有原因・数値対応・補正・元ページ保持面の互換、設定・選択・保存失敗・compare-dir・静的リンク、全回帰とゴールデン、実CLIの資源を検証する。旧入力2方向と負例18方向は見送りのままにする。

承認された接続案に従い、以下の出力と予約の契約を製品仕様へ反映して実装する。Windows・実帳票・保留された手動確認は別の受け入れとして残す。

## 承認範囲の出力・予約契約（2026-09-27）

既存の公開APIは全対応ページの条件を維持する。製品の計画だけが、凍結済み文書・推定候補・実効設定を確認して末尾専用の再検証を呼ぶ。曖昧な境界だけを置換し、候補配列の順序とIDを変えない。追加経路は全境界が同方向の実際の跨ぎで連結する一連鎖に限定し、非送り証明や数値対応との組合せを追加しない。元画素・局所支持・全ページ採用・末尾の全非白残余検査は既存経路に通す。

共有成分とその末尾送りリンクにだけ、任意の `auxiliary_bands` 配列を追加する。要素は既存 `ReportFlowEndpoint` と同じ形式で、元画像Oの側・ページ・矩形・mm・保存済み帯画像・空の `structures` を持つ。元の送りリンク端点を再利用し、末尾の本文を過不足なく覆う送り先一つだけを許す。成分の `structures` は実構造のみ。補助帯を件数や原因へ加算しない。補助帯のない既存成分／リンクではこのプロパティを省略して旧JSONを維持する。HTMLでは片側の補助帯・未比較であることと元帯画像への参照を示す。

曖昧候補の予約は既存の `1,024 + 行×2,048 + ページ記述×256 + 候補×512` B、選択した各境界の `1,024 + 跨ぐ行×1,024` Bを用い、確保前に文書記述・数値対応・非送り証明を引いた64MiBの残りへ計上する。適格変位・本文への参照も固定予約に含む。証拠が未成立／上限超過なら全追加証拠を破棄し、既存候補を返す。

共有集約は独立成分の失敗後に検証し、一時領域の予約は再利用できる。末尾集約の既存予約 `1,024 + 行×2,048 + ページ×512 + リンク×1,024 + 実構造×2,048` Bに、共有原因の既存計上量と補助帯1個につき256B（成分・リンク・出力の参照配列を含む）を加える。成功時は末尾予約と共有記述量を別々に保持し、その合計を同じ残予算内へ収める。上限ちょうどは許可し、1B不足は `terminal_descriptor_limit` で全成分・全追加予約を取り消す。C/Dと内容・未集約件数は維持する。再試行による累積消費はしない。

この契約の実装と検証結果は[製品接続記録](../verification/t3-1c-unpaired-shared-integration.md)に記録する。
