# T3-1c 共有原因の未成立6方向の前段診断

2026-09-23。共有原因の製品接続後の続行指示に基づき、三ページ連鎖・同一ページ二原因・共有原因→独立原因の各両方向を独立に診断する。製品の推定・元帯検証・写像・支持・採用・集約、設定、JSON／HTMLは変更しない。

## 観測する条件

現推定器は、同じページ内の全文一致行が示す正の変位を集め、既存の最大移動量と最小支持行数を満たす変位が一つの場合だけ、その高さの末尾帯→次ページ先頭帯を候補にする。二つ以上なら端点なしの `ambiguous_displacement` となる。この結果と、実際の一意な共通行の物理ページ対応を突き合わせる。

- 各ページの変位ごとの元本文・支持数・範囲内かどうか。
- 各境界を実際に跨ぐ行と対応先、跨がないことを示す文書全体の共通行順序。
- 全幅末尾／先頭を完全な行で埋めるか、元帯全画素一致と置換比較が成立するか。
- C/Dの局所未対応帯で、前後それぞれ二行の元本文支持があるか。
- 文書ゲート、既存採用評価、内容クラスタ、実構造ID、因果集約までの成立範囲。

## 独立実験

固定PDFから取得した全本文が両側で一意、共通行の順序が等しく、全物理ページが対応する場合に限定して共通行の実ページ移動を求める。隣接しない跨ぎや同一境界の逆向きの混在を拒否し、跨ぐ全行が元の末尾帯／先頭帯を隙間なく占める場合だけ候補範囲を作る。最大移動量と、同じ変位を裏付ける同一ページの元本文支持も別々に確認する。

跨ぐ共通行がない境界では、候補の長さを任意に選ばず「共通行の跨ぎなし」を診断記録へ残す。これは現在の非送り証明の製品仕様を拡張するものではない。元の候補を消して製品出力を変える処理にも接続しない。

候補支持が不足する場合も、元帯・写像のどこで止まるかを調べるため後段を観測できる。ただし支持不足の候補は最終採用の条件を満たさない。帯の全文／全画素一致を支持行数の代わりにはしない。既存のPageFlowSurface・PageFlowAdoption・PageFlowAggregationを独立ツールから呼び、製品クラスを変更しない。診断内の反射は製品APIに漏らさない。

既存の固定26方向を対照として全実行する。元の実CLIと前回の出力を照合し、診断結果とは区別する。C/D転写と生差分マスクを独立Pythonで確認し、製品103ソースのSHA256不変を確認する。新しいPDF・依存・しきい値は追加しない。

## 完了境界

この工程の成果は、各未成立方向の具体的な不足、条件を緩めず成立し得る候補の範囲、次に必要な検証と接続案まで。診断で一部が成立しても製品の受け入れ済みに変更しない。候補支持不足や構造帯の根拠不足が残る方向は未成立のまま保つ。A4未成立9条件、異符号・片側ページとの一般化、数値変更行自体の跨ぎ、Windows・実帳票・大規模性能、保留されたブラウザー確認も今回の受け入れには含めない。

## 診断結果と次の接続案

[診断記録](../verification/t3-1c-shared-inference-diagnosis.md)に具体的な行と変位を記録する。三ページ連鎖と共有原因→独立原因の計4方向は独立診断で成立し、同一ページ二原因の2方向は支持と末尾構造の条件が不足する。後者の期待は変更しない。

次工程で推奨する接続範囲は、上記4方向の原因になった `ambiguous_displacement` に限定した候補の再検証とする。現在の候補推定全体を診断版に置換しない。

1. 現推定器が出す候補と既存IDを先に固定し、成功する従来経路を維持する。失敗した境界・方向と、元本文の支持を満たす変位群を保持する。ページ選択・片側ページ・行の重複・順序不一致・非隣接の跨ぎは追加の救済対象外とする。
2. 実際に跨ぐ一意な共通行がある場合、その全行が末尾／先頭の帯を隙間なく占め、その高さに一致する既存の適格変位が一つだけあることを要求する。最大変位や最低支持数は変えず、部分的に一致する短い帯・最長変位というだけの選択はしない。元帯の全画素一致・置換比較、C/D、採用条件を改めて通す。
3. 共通行が跨がない場合も、それだけで候補を除かない。100px・200pxなど全ての適格変位から仮端点を作り、各候補の全行が反対側の同じ物理ページへ対応することを既存の `PageFlowNonflow` 条件で要求する。どれか一つでも不明なら文書全体を見送る。現仕様の端点なし `ambiguous_displacement` をどの境界の証明と結び付けるか、元の候補IDと複数の仮端点をJSON／HTMLへどう記録するかを接続前に確定する。仮端点を「画像検証済みの送り」と表示しない。
4. 追加の行索引・候補変位・仮端点・証明を既存64MiB記述予算へ確保前に計上し、候補数128・行数等の上限を維持する。全ての適格変位を検証できない場合の打ち切りは、候補を間引くのでなく全体見送りとする。上限ちょうど／1B超過と一部の証拠欠落を検証する。
5. 元本文・元文書記述との結び付けを保持する。今回の固定入力は数値変更・全体補正・除外を含まない。数値対応IDを候補の全文一致・支持へ使わず、縦補正はGの候補をOへ戻して元帯を証明し、既存の除外・領域・支持条件を変えない。組合せを実PDF／CLIで別に確認する。
6. 固定26方向と既存104方向、数値50方向、既存の縦補正・共有原因併用条件を旧新CLIで照合する。今回対象の4方向だけを追加成立とし、未成立の同一ページ二原因2方向と負例12方向は維持する。追加4方向のC/D・生差分・実構造ID・集約・raw evidence・HTML参照、compare-dir、明示選択、入力変更・保存失敗、全テスト、実CLI時間・RSSを確認する。

この計画段階では製品への接続を行っていない。描画が異なるA4入力、未対応の同一ページ二原因、候補に数値行自体を使う一般化や新しい構造分割は別の検討に残す。
