# T3-1c 複数原因を分けるための独立検証

2026-09-23。縦方向の全体補正の接続後の続行指示に基づく、設計と独立検証。製品の単一原因の採用条件・件数・比較経路はこの工程では変更しない。

## 分離候補の境界

同じ送り連鎖の途中に二つの挿入がある場合、後半の移動は両原因の累積量になる。同じ実構造IDを各原因のグループへ重複させたり、便宜的に分割して新しいIDを作ったりしない。現在の二挿入の未集約期待を維持する。

まず、ページを頂点、検証済みの隣接送りリンクを辺とする連結成分で、異なるページ群に完結する原因だけを分離する案を試す。成分内には原因一つの従来の全条件を要求する。二原因が同じ成分へ入る場合は文書全体の集約を見送る。同一ページ内の独立原因や、同じ移動に複数原因が寄与する一般化は対象外。

## 検証条件

1. 文書全体の範囲・画像証明・行採用が成功し、選択範囲に欠落がない。分割前に本文の全体一意性と共通行の順序を確認する。
2. 共通行がページをまたぐ場合、その両ページは同じ成分に属する。欠けたリンクを成分の切れ目と誤認しない。
3. 各送り成分に既存の単一原因集約器を適用する。ページ番号だけ局所化し、本文・Gの座標・構造ID・比較件数・検証済みリンクを変更しない。
4. どの送り成分も成功した場合にのみ採用する。一つでも不成立なら、成功した成分も含めて集約を取り消す。
5. 送りのないページは構造変更がなく、本文の座標・順序・本文がA/Bで一致する場合だけ中立とする。内容クラスタはそのまま残す。
6. 元の実構造参照とグループ所属が一対一で、全構造を過不足なく説明する。同じIDを二回使わない。全体件数U、所属する実構造n件、原因群k件なら集約後は `U - (n - k)`。内容クラスタを減らさず、網羅性を引き上げない。
7. O/Gの区別を維持する。送り・構造の論理範囲はG、元帯画像の証明はO。分割は画像比較や元画像の加工を行わない。

単一原因で従来成立する入力は、従来の結果をそのまま返す。検証ツールへケース名・生成時の正解境界を入力しない。

## 証拠を作る範囲

独立した二つ／三つの送り、挿入と削除の併存、三ページ連鎖と別の原因、中立ページ、内容色変更を合成PDFから確認する。A/B逆転、影響が重なる二挿入、一方の成分の証明失敗、数値変更、文書全体での反復本文を負例にする。

本文・リンク・構造・ページの列挙順、欠落、重複、所属変更、全体ゲート、選択範囲、除外、網羅性を変更して監査する。比較コアから実際に得た構造IDとC/Dを使い、Pythonの独立した編集列と参照マスクでも確認する。実CLIは従来の未集約結果を維持することを確認し、独立ツールの件数と区別する。

この工程の成果は成立範囲・残る制約・製品接続案まで。A4未成立9条件、数値変更を含む写像、横補正・片側ページとの一般的な組合せ、Windows・実帳票・ブラウザー保留の受け入れにはしない。

## 独立検証で分かった前段の課題

そのままの製品推定器では、あるページ群の終わりにも正の行ずれがあると、次のページ群へ候補を作る。候補帯の行は同じページの相手側へ既に対応しているが、次ページ先頭とは文字が異なるため `text_mismatch` となり、文書全体の送りを見送る。最初の12ケース・24方向では、集約を期待した12方向がこの段階で未成立だった。その記録は `out/t3-1c-multiple/first/` に保持した。

この境界の証明を先に追加した独立ツールで、次のすべてを確認してから候補を「送りではない」と分類した。

- 全物理ページがA/Bで対応し、選択範囲の省略がない。レイアウト・本文範囲は既存の条件で準備済み。
- 文書全体の本文が各側で一意で、共通行の順序が変わっていない。
- 対象は、端点を持つ `text_mismatch` の候補だけ。画像不一致、曖昧な移動量、反復本文をこの分類で救済しない。
- 候補元と候補先の帯全体が完全な本文行で隙間なく埋まり、その全行が反対側の**同じ物理ページ**に一意に対応している。
- どの共通行もこの物理ページ境界を跨いでいない。欠けた送りリンクを切れ目として扱わない。

この証明は画素一致の証明ではない。該当帯を内容比較から外さず、対応する同一ページ内の画素比較へ残す。候補帯の末尾に色変更を置いた対照では、生差分2,850画素・内容クラスタ1件がC/Dに残った。文字を555→556へ変えた対照は同一ページ対応を証明できず、全体を見送った。

## 検証結果

[結果と証拠](../verification/t3-1c-multiple-causes.md)。14ケース・28方向で採用期待14／見送り期待14が一致した。独立した二原因10→2、三原因15→3、連鎖と別原因13→2、内容変更保持11→3。影響が共有される二挿入は7のまま、独立原因と共有原因の併存は12のまま。別ページの局所原因だけが追加された場合も7のままとした。

製品の変更ではなく独立ツールの結果。製品CLIは、誤候補を含む二原因文書では現在の見送りによる18件を維持する。独立ツールの10は、境界を証明して送りを採用したC/Dのページ別内訳Uであり、現製品18件を直接2件へ集約した値ではない。

## 製品接続の具体案

2026-09-23の続行指示に基づき、以下を製品へ接続した。[接続結果と成立範囲](../verification/t3-1c-multiple-cli.md)を参照。以下は承認時の接続条件。

1. `IndependentBoundary` の証明を、Coreの独立した型へ移す。診断ツールの反射による `PageFlowPlan` の構築は製品へ持ち込まない。省略されたページ、反復本文、未準備のレイアウト、反対側対応の欠落があれば証明を発行しない。
2. すべての候補と元の順序・リンクIDを保持し、証明できたものだけを送りの検証対象から外す。未解決の候補を無条件で捨てない。文書ゲートへ「検証済み送り／同一ページ対応済み／未解決」を区別して渡す。C/Dの構造帯には検証済み送りだけを使う。
3. JSON／HTMLには候補を見送った理由と同一ページの対応先を残す。現在の `page_flow.links` の `status: skipped`・`image_status: not_performed` に理由 `same_page_rows_not_flow` と追加の証明情報を持たせる案とする。画像一致検証に合格した送りと表示上で混同させない。利用者向け端点・対応先はO、Coreの論理範囲はG。元のリンクIDが集約グループから参照できるようにする。
4. 送りを全体採用できた後、ページ群が交わらない成分へ分け、各成分の単一原因を既存条件で検証する。新規の複数原因対応は全選択ページが両側で揃う場合に限定する。既存の単一原因と片側ページの経路は維持する。片側ページと複数原因の一般化は別途検証する。
5. 成功した各成分を既存の `groups[]` に別々に出し、原因・実構造・リンクを重複させない。一つでも未説明の成分・構造があれば全グループを取り消す。`difference_count` は選択されたC/Dのページ別内訳U、`aggregated_difference_count` は `U - Σ(nᵢ - 1)`。内容クラスタ・網羅性・終了コードを維持する。
6. 証明情報の追加保持量を既存の64MiB予算へ計上し、本文文字列・画像・行ハッシュを重複保持しない。従来の行数・候補数・ページ数等の上限を緩めない。無効時の収集・再描画を増やさない。
7. 実CLIの固定28方向と既存76条件、縦方向の全体補正、除外・領域、選択範囲・上限、入力変更・保存失敗、compare-dir・JSON／HTML、raw evidenceを確認する。新規C/Dのページ別内訳も明示的に期待へ固定する。製品接続後に全テストと時間／RSS／描画回数を検証する。

同じページ群に複数原因がある場合、同じ構造IDを原因別に割り振る一般化、数値変更を含む写像、横補正、A4未成立9条件、Windows・実帳票・ブラウザー保留は対象外に残す。
