# T3-1b 事前検証：帯の継ぎ目に残る差分

2026-09-22。基準は v0.1.3（`f77ac1c`）。**T3-1b は未完了。製品への組み込みは、タスクに定めた停止条件により保留した。** 比較コア・参照実装・既存ゴールデンの期待値は変更していない。

後続の検証：以下の第一候補「比較用の帯を両側とも白にする案」は、追加の指示を受けて試行した。本物の変更の検出を失うため不採用。最新の状況は [白い帯の検証結果](t3-1b-white-band.md)を参照。以下は対策の検証前に確認した継ぎ目の記録。

白い詰め物の内側だけを生差分から除外する方式では、縦罫線の継ぎ目に偽の差分が残る。正しい帯の対応を与えても発生するため、行の LCS やベースライン推定の精度を上げるだけでは解消しない。

## 試行の範囲

[再現プログラム](../../tools/ReportDiff.RowProbe/README.md)を追加した。行推定や CLI の rows 設定を実装する前に、既存の PageMap へ既知の正しい帯の対応を渡し、その出力を既存の比較器で調べた。

- 画像 12 条件：縦罫線 0 / 1 / 2 / 3 / 4 / 6px、normal / strict。
- 合成 PDF 24 条件：縦罫線 0 / 0.24 / 0.48 / 0.72 / 0.96 / 1.44pt、行挿入のみ／挿入＋合計数値変更、normal / strict。
- PDF は T2-3 と同じ自作 Type3 フォントを埋め込み、PdfPig で単語とベースラインを取得した。外部フォント・実帳票・新規依存は使用しない。
- 300dpi、PDF の描画サイズは実測 999×1250px。1 行は 100px、挿入位置は y=400px。文字と直下の横罫線を同じ帯に含め、切断行を横切るのは縦罫線だけとした。

PageMap は次の対応を持つ。末尾は両入力とも純白で、内容のある画素は失わない。

| 比較キャンバス y | 元 A の y | 元 B の y | 扱い |
|---|---|---|---|
| [0,400) | [0,400) | [0,400) | 対応する帯 |
| [400,500) | 詰め物 | [400,500) | B の挿入帯。生差分から除外 |
| [500,1250) | [400,1150) | [500,1250) | 対応する帯 |
| [1250,1350) | [1150,1250) | 詰め物 | 純白の余白。生差分から除外 |

挿入だけの全条件で、除外帯以外の A/B の BGR 画素は完全一致した（最大画素差 `pairedNorm=0`）。比較対象に現実の内容変更がないことを、比較器とは独立した直接の画素差で確認した。

試行の除外は上表の整数 px の帯と厳密に一致させた。px→mm→px の丸め誤差で外側の 1px まで消すと継ぎ目の残差を過小評価するため、既存の floor / ceil 後の矩形を検査した。製品の換算規則は変更していない。

## 観測結果

normal では以下の結果となった。生差分画素数は、挿入帯と末尾余白を除外した後の値。

| 縦罫線幅 | 挿入のみ：生差分／クラスタ | 挿入＋数値変更：生差分／クラスタ |
|---|---|---|
| なし | 0 / 0 | 69 / 1 |
| 0.24pt（1px） | 0 / 0 | 69 / 1 |
| 0.48pt（2px） | 0 / 0 | 69 / 1 |
| 0.72pt（3px） | 2 / 0 | 71 / 1 |
| 0.96pt（4px） | 4 / 0 | 73 / 1 |
| 1.44pt（6px） | **8 / 2** | **77 / 3** |

strict は全罫線幅で挿入のみが 0 / 0、数値変更ありは 90 / 1。数値変更は `SUM TOTAL 555` → `SUM TOTAL 111` で、対応する通常の帯に残した。画像試行でも、6px の縦罫線で normal に余分な 8px・2 クラスタが出た。

PDF の全 24 条件で、Python の `reference/prototype.py` と C# の生差分マスクが全画素一致し、状態・クラスタ数・矩形・画素数も一致した。C# 側だけの実装不具合ではなく、現在の比較式と白い詰め物の組合せで発生する。

さらに Python で、切断位置を y=392 / 396 / 398 / 399 / 400 / 401 / 402 / 404 / 408px に変更し、A/B を入れ替えた計 18 条件を確認した。全条件で対応する元画素は完全一致し、normal に 8px・2 クラスタが残った。切断位置の小さな変更や A/B 交換では解消しなかった。

## 原因

normal の余分なクラスタは `(x=101, y=399, w=4, h=1)` と `(x=101, y=500, w=4, h=1)`。挿入帯 `[400,500)` の直前・直後にあるため、帯の内側だけを除外しても残る。この 8 画素は、元の A/B とも黒（BGR 0,0,0）で同一。

5.2 の 3×3 ぼかしは、A の隣接する白い詰め物を参照する。一方、B では挿入行の縦罫線が続いている。ここで L のぼかし後の差が約 33.333、判定しきい値が `3 + 0.3 × 100 = 33` となるため候補が生じる。二段目を経ても各境界に 4 画素が残り、既定の最小クラスタ画素数 4 を満たす。

3 / 4px の罫線でも余分な生差分は発生しており、現在のノイズ除去でクラスタにならないだけ。細い罫線の成功例だけで採用可と判断しない。しきい値・ノイズ条件を緩める、strict を強制する、帯の外側まで黙って除外する対応も行っていない。

## 停止理由と次の検討案

[TASKS の T3-1b](../TASKS.md) は次を停止条件としている。

> 整列後の比較に、既存の 5 章以外の判定が必要になった場合（例：帯の継ぎ目に偽の差分が出る）は、式を変えずに止まって報告する。

今回これに該当した。R01 の「挿入 1・移動 1・クラスタ 0」を、縦罫線を許容する白い詰め物方式で保証できない。R02 でも本来の数値変更に余分なクラスタが加わる。偽のクラスタを正しい検出としてゴールデンへ登録せず、T3-1b を未完了のまま残した。

次は、**表示用の整列画像と、比較前処理で対応のない帯を扱う方法を分ける設計・検証**を推奨する。以下は未承認・未検証の候補で、現仕様の変更として扱う。

| 案 | 調べる内容 | 主な確認点 |
|---|---|---|
| 比較用の一時画像では、片側帯を両側とも同じ白にしてから 5 章へ渡す | 表示と raw evidence は元のまま、比較の入力だけで片側帯の内容が近傍演算へ入ることを防ぐ | 人工的な境界が、隣接する本物の差分のしきい値・インク連結・二段目の group に与える影響 |
| 元画像で作った特徴量と帯の写像を組み合わせる | 白い詰め物で特徴量を再計算せず、元の近傍情報を使えるか調べる | 全体補正・領域別設定・二段目の探索・クラスタ化との整合。実装規模が大きい |
| 初期対応を純白の切断行だけに限定する | 縦罫線が切断行を横切るページを見送る | 現タスクの対応範囲を狭めるため、利用対象と R 系の条件の見直しが必要 |

最初の案を検証候補の第一候補とするが、安全性の結論はまだ出していない。比較式は変えず、前処理の変更を独立した試行で評価する。最低限、今回の 6px 罫線、A/B 交換、切断位置、境界の直前・直後の小数点／細線／色・塗り変更、罫線の延長・太さ変更、近接する複数の挿入、normal / strict / loose、regions / exclude の境界、既存 42 ゴールデンを使う。本物の差分の検出を維持できる場合だけ、改訂仕様として T3-1b へ戻す。
