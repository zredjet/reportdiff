# PERF-2f 初期差分SIMDの追加効果と採否

確認日：2026-09-21。対照は行並列化済みの `71de388`。結論は **現時点では製品へ導入しない**。比較コアのコードは対照のまま維持し、試作は [評価ツール](../../tools/ReportDiff.CandidateBenchmark/README.md) として保存した。

初期候補の抽出自体は速くなるが、保存までの全体時間は一貫して改善しなかった。厳密比較の全面変更では遅くなる条件もある。現状ではCPU別の経路・端数・丸めを維持する負担に見合う全体効果が確認できないため、現在のスカラー式による行並列化を継続する。Windows等での効果まで否定する判断ではない。

## 試作した方式

.NETの `Vector128` / `Vector256` を使用し、ハードウェア対応を判定して256bit→128bit→スカラーの順に選択する。3ベクトルを読み、128bitなら4画素、256bitなら8画素の全チャネルをまとめて比較する。比較結果のビットを3つずつORして画素の0/255へ戻す。全チャネルを計算するため、現行の「最初に差が出たチャネルで打ち切る」速度上の利点は維持しない。

入力は既存のfloat32特徴量を読み取り専用で共有し、候補マスクは1枚だけ確保する。追加の全ページ画像・マスク・特徴量コピーを作らない。4workerでは担当行が重ならず、段階間の並列実行も追加しない。小画像は既存の100万画素の境界で逐次実行する。

乗算と加算を分け、FMAを明示的に使用しない。厳密な `>`、3チャネルのOR、エッジ許容0ではコントラストを読まないことを維持する。ベクトルで処理できない末尾は既存スカラー式へ戻す。読み込む全区間をSpan.Sliceで検証した後にLoadUnsafeし、担当区間の外を読まない。

APIの根拠はMicrosoftの [.NET 10 Vector128](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.intrinsics.vector128?view=net-10.0) と [Vector256](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.intrinsics.vector256?view=net-10.0)。一般的なSIMDの速度を受け入れ根拠にせず、以下の実測で採否を判断した。

## 判定結果と復帰経路の検証

製品と評価ツールのReleaseビルドは警告0・エラー0。製品の全 **996件成功、失敗・スキップ0**。

評価ツールの独立検証は、SIMD有効・無効のそれぞれで **12,568照合が一致**。次を含む。

- 要素数0〜33、127/128/129/1025、開始画素0/1/2/3/7、ランダムな有限float32値、エッジ許容0/0.3/0.6、しきい値0/3.1/1000。
- 各チャネル・各レーン・ベクトルをまたぐ画素、差の正負、A/B両方のコントラスト最大値、しきい値の直前・同値・直後。
- FMAと個別の乗算＋加算で丸めが異なる1,000条件。融合演算へ置き換えていないことを出力で検証。
- 幅1/73px、高さ1/7/513px、1/2/4/8worker、担当行、入力配列不変、出力区間前後の番兵が不変。
- Scalar / Auto / Vector128 / Vector256 の4経路。`DOTNET_EnableHWIntrinsic=0` ではAutoがScalarを選ぶことも記録。

このMacでの自動選択はArm64のVector128。Vector256の照合はハードウェア非対応の固定幅経路であり、Windows x64のSSE/AVX命令の実機検証とは区別する。非対応CPUの実機確認も行っていない。

現行4並列・スカラー逐次・SIMD逐次・SIMD4並列の4構成で、100スナップショット（37ゴールデン、画像端/ROI/帯境界/設定60、大画像3）が完全一致。差分マスクのSHA-256、統計、クラスタ、分類／移動注釈、警告を含む。

公開帳票のCLI52実行とステージ計測32実行、計 **84実行**（ウォームアップ込み）で、JSONの `schema_version/tool/inputs/config/summary/warnings/pages` と全PNGの名前・SHA-256が一致。生成日時は比較対象外。HTML生成は時間に含むが、バイト一致は検証対象外。

## 初期候補抽出の速度

Apple M4 Max（16コア・128GiB RAM）、macOS 26.5.1、.NET 10.0.12、Release。公開A3工程表の通常比較。構成を交互・往復順に実行し、ビルド・テスト・別の計測と同時実行しない。各構成ウォームアップ1回後3回の独立プロセス、中央値。

| 解像度 | スカラー逐次 | 現行4並列 | SIMD逐次 | SIMD4並列 |
|---|---:|---:|---:|---:|
| 300dpi | 43.41ms | 12.30ms | 14.46ms | 7.39ms |
| 400dpi | 77.06ms | 21.41ms | 23.61ms | 10.50ms |

候補抽出だけなら300dpiで約40%、400dpiで約51%短縮する。しかし今回の単ページでは全体の約1%しか占めておらず、削れる実時間は約5ms／11msだった。SIMD逐次は現行4並列に近い時間で動作するため、将来CPU使用量や並列予算を主目的に評価する場合には検討材料となる。今回はCPU時間・消費電力を測定しておらず、その改善は主張しない。

## 保存までの時間と最大RSS

CLIの起動・PDF描画・比較・注釈・PNG/JSON/HTML保存・終了まで。`--save-all-pages` を指定。各構成ウォームアップ1回後、単ページは7回、4ページは5回、20ページは3回測定した。RSSは `/usr/bin/time -l`、GBは10^9bytes。4/20ページは同じ公開ページを繰り返したPDF。

| 条件 | 現行 | SIMD試作 | 短縮率 | 現行RSS | SIMD RSS |
|---|---:|---:|---:|---:|---:|
| A3・300dpi・1ページ | 1.328秒 | 1.328秒 | -0.03% | 1.969GB | 1.966GB |
| A3・400dpi・1ページ | 2.044秒 | 2.037秒 | 0.34% | 3.508GB | 3.505GB |
| A3・300dpi・4ページ | 3.445秒 | 3.489秒 | -1.29% | 2.153GB | 2.152GB |
| A3・300dpi・20ページ | 14.958秒 | 14.905秒 | 0.35% | 2.263GB | 2.263GB |

短縮率の負数は遅くなったことを表す。1/4/20ページで一貫した全体改善は確認できない。これは今回の入力・機器・反復数の観測結果であり、差のすべてをSIMDの因果効果と断定しない。GCや実行時のばらつきも含む。メモリはほぼ同程度で、メモリ削減としては評価しない。

合成A4・300dpiの比較コアでは、局所変更が93.29→90.65ms、局所変更＋全体1pxずれが99.42→101.62ms。各構成5回の中央値、検出の主要統計は一致。既存ハーネスは測定前に強制GCを行うため、通常CLI/RSSとは別の補助結果として扱う。

## 次に優先する対象と未確認範囲

300dpiの現行版のステージ中央値は、注釈画像の生成・保存227ms、位置ずれ探索205ms、特徴量生成を含む前処理196ms、PDFテキスト注釈195ms、候補抽出12msだった。前処理・探索は比較コアの内数であり、上位の「比較」時間と重複して合計しない。次の改善調査は、この残る処理の内訳から選定する。

- Windows x64のSSE/AVX実機、低メモリPC、異なる実帳票、20ページを超える大量ページ・長時間運用は未確認。現在の製品にはSIMDを追加しないため、これらを新しいリリース条件にしない。
- 命令セットによって集約や読み込みのコストは変わり得る。Windows実測やCPU使用量の評価で明確な利点が出た場合は、保存した試作から再検討できる。
- 性能改善全体のWindows・低メモリ・長時間確認は、既存のPERF-2の残件として維持する。追加の製品実装・配布物更新・pushは行わない。

## 証跡と再実行

製品DLLは再ビルドでGit revisionの埋め込みが更新され、保存済み対照DLLとSHA-256が異なる。製品コードの不変はsrcの差分なしと、全メソッドのILバイト列一致で確認した。両DLLのハッシュとIL照合結果も証跡へ記録した。

数値・各実行の時間/RSS/一致・入力とDLLのSHA-256・最終評価ツールと試作ソースのSHA-256は [perf-2f-candidate-simd.json](perf-2f-candidate-simd.json)。再現可能な合成データの評価ツールはgitに含める。公開PDF・旧DLL・画像・CLIに接続した試作用Core・計測スクリプトはgit管理外に保存した。

```sh
dotnet build -c Release --disable-build-servers -m:1 -p:UseSharedCompilation=false -p:NuGetAudit=false --no-restore
dotnet test -c Release --no-build
dotnet run -c Release --project tools/ReportDiff.CandidateBenchmark -- verify
DOTNET_EnableHWIntrinsic=0 dotnet run -c Release --project tools/ReportDiff.CandidateBenchmark -- verify
dotnet run -c Release --project tools/ReportDiff.CandidateBenchmark -- measure > micro.json
```

既存のローカル測定資材を使う再実行は次のとおり。出力先がある場合は測定名を変更する。旧DLLと入力の保存、テストIPC/RSS取得のホスト実行権限が前提。

```sh
python3 out/perf2f-simd/check.py
python3 out/perf2f-simd/measure.py probe 300 scalar-serial,baseline,simd-serial,simd 3
python3 out/perf2f-simd/measure.py probe 400 scalar-serial,baseline,simd-serial,simd 3
python3 out/perf2f-simd/measure.py cli 300 baseline,simd 7
python3 out/perf2f-simd/measure.py cli 400 baseline,simd 7
python3 out/perf2f-simd/measure.py cli4 300 baseline,simd 5
python3 out/perf2f-simd/measure.py cli20 300 baseline,simd 3
```

比較用DLLの `baseline` は `71de388`、`scalar-serial` は候補抽出のworker上限だけ1、`simd` は同じ行分担にSIMD試作を接続、`simd-serial` はそのworker上限だけ1とした。他段階の実行方法は共通。独立した最終評価ツールも同じベクトル計算を使うが、既存スカラー処理への呼び出し名だけ製品の内部APIに合わせている。
