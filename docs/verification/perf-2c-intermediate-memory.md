# PERF-2c グループ生成の中間画像メモリ

確認日：2026-09-21。変更前は区間走査・グループ並列探索を実装した `23158f3`。4ページの最大RSS中央値が約0.10GB増えた残件を調査し、中間Matの寿命を短縮した。比較式、精度、既定値、出力、worker数は変更しない。

## 調査と判断

公開A3・300dpiの区間索引は51,966区間・139グループ、構築配列の要素は約0.626MBであり、容量だけでは約100MBのRSS差を説明できない。前回の逐次版でも増加を観測しており、worker数だけに原因を求めることもできない。

診断用に、探索変更前の `4d22615` と `23158f3` の通常CLIで4ページを比較し、`dotnet-trace` の `gc-verbose` を取得した。現行版では4ページ目にgen2の回収が入らず、終盤のLOHサイズが約541MBとなる実行があり、旧版の同じ区間では約262MBだった。約17.4MBのbyte配列と約69.6MBのint配列をページごとに多数確保している。LOHサイズは空き領域を含み、生存オブジェクト量やRSSとは異なる。トレース自体も回収タイミングへ影響し得るため、約100MBの全量を特定の配列・GCイベントへ割り当てた結論ではない。

コードでは、インク・インクラベル・候補・候補膨張・領域の和・領域膨張・最終ラベルの各Matが、グループ生成メソッドの終端まで重なっていた。GC時期による大配列の残留に、このネイティブ画像の重複保持が重なる。これを直接減らす変更を採用した。恒久的な参照保持やメモリリークを原因と断定する証拠は得ていない。

比較した案：

- ラベル等をMatのSpanで参照し、管理配列へのコピーを除く案は、単ページと4ページで削減したが、20ページでは約2.285→2.336GBとなった。全体の確保・回収パターンも変わるため採用しない。
- 特徴量のネイティブ使用量を `GC.AddMemoryPressure` で通知する試作も測定したが、今回の製品変更には採用しない。特徴量はDisposeで解放しており、GC発火の調整より所有範囲の短縮を優先した。このAPIはGC判断に関与し、追加・除去量の一致が必要である（[Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/system.gc.addmemorypressure?view=net-10.0)）。
- 管理配列の構成を維持し、中間Matだけを各段階で解放する案を採用した。強制GC、GC設定変更、プールへの長期保持は追加しない。

試作値は案の選別用。以下の表は最終DLLを使用した独立の測定。

## 実装

`TolerantDifference.GroupRegion` が候補と接触インクの領域を生成する。インクラベルを配列へコピーした直後、候補膨張を配列へコピーした直後に、それぞれのMatをusingで解放する。`Groups` は領域を膨張した後、入力領域を解放してから最終ラベル画像を生成する。例外時もusingの範囲で解放する。

明示的に保持するグループ生成用Matの最大合計は13bytes/画素から5bytes/画素へ減る。4960×3508pxでは約226.2→87.0MB（約139.2MB減）。入力インク、カーネル、OpenCV内部の作業領域、管理配列、アロケータが保持する空き領域はこの計算に含まない。この差がそのままプロセスRSSの差になるとは限らない。

管理配列の形式、探索索引、並列処理、分類へのインク再利用とその所有期間は維持する。特徴量・初期差分・ページ間の並列化、SIMDは今回の対象外。

## 検証

Releaseビルドは警告0・エラー0。既存の全 **923件成功、失敗・スキップ0**。グループ1/2/4/8並列・矩形復帰・全ページ参照、非連続Mat、画像端、300/400dpi、インク再利用、例外時worker終了を含む既存回帰を実行した。新しい判定は追加していないため、テストケースの追加はない。

保存済みの変更前DLLと最終DLLで、37ゴールデン・60の画像端/ROI/帯境界/設定・3大画像、合計100条件のスナップショットが完全一致。raw/label/removalマスクのSHA-256、統計、クラスタ、分類・移動注釈、警告を比較した。

以下の最終CLI **40実行**（ウォームアップ込み）で、JSONの `schema_version/tool/inputs/config/summary/warnings/pages`、全PNGの名前・SHA-256が一致。生成日時は比較対象外。HTMLは生成と処理時間の対象だがバイト一致は主張しない。

## 時間・最大RSS

Apple M4 Max（16コア・128GiB RAM）、macOS 26.5.1、.NET 10.0.12、Release。伊勢市の公開工程表1組。4/20ページは同じページを繰り返したPDF。通常CLIの起動からPDF描画、比較、注釈、PNG/JSON/HTML保存、終了まで。`--save-all-pages` を指定。RSSはmacOSの `/usr/bin/time -l`、GBは10^9bytes。

各構成ウォームアップ1回。4ページは7回、ほかは3回の独立プロセスで測定し、変更前後を交互・往復順に実行した。最終測定中はビルド・テスト・別ベンチマークを並走させていない。表は中央値。

|---|---:|---:|---:|---:|
| A3・300dpi・1ページ | 1.598秒 | 1.595秒 | 1.996GB | 1.924GB |
| A3・400dpi・1ページ | 2.449秒 | 2.429秒 | 3.578GB | 3.496GB |
| A3・300dpi・4ページ | 4.383秒 | 4.371秒 | 2.177GB | 2.108GB |

4ページのRSS範囲は変更前 2.080〜2.182GB、変更後 2.009〜2.111GB。20ページは変更前 2.286〜2.292GB、変更後 2.215〜2.219GB。GC・ネイティブアロケータの動作による実行間のばらつきがあり、中央値だけで固定の上限を定義しない。4ページで増えた約0.10GBをすべての実行で完全に解消したとは主張しない。

集計・全実行・入力/DLL/変更ソースのSHA-256・診断用GCイベントは [perf-2c-intermediate-memory.json](perf-2c-intermediate-memory.json)。機密帳票や生成画像はコミットしない。
