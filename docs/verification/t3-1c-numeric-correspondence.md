# T3-1c 数値変更を含む行対応の独立検証

2026-09-23。[限定した設計](../planning/t3-1c-numeric-correspondence.md)を独立ツールで検証した。数値の変わった行を同じ行として対応付けても、その変更を内容差分として保持できる例を確認した。**製品の動作は今回変更していない。** 製品97個のC#ファイルと4個のプロジェクトファイルは着手時および前回の複数原因接続時とSHA-256が一致する。

## 入力と成立範囲

25ケース・50PDF・108物理PDFページをA/B両方向の50実行で確認し、事前の採否期待50件すべてが一致した。生成時の正解を行対応器に渡さず、実PDFの文字層・位置と描画画素から検証する。元の末尾 `555→556` の2PDFは以前の `flow-number-change` と全バイト一致し、複数原因の数値変更4PDFも以前の固定入力を使う。

対応は、同じ物理ページ、一意な元本文と数値欄以外のラベル、少なくとも二つの非数値トークン、直近二行の完全一致と同じ相対位置を要求する。ASCIIの符号付き整数・小数の独立したトークンだけを扱う。桁区切り、英数字IDの一部、数字だけの行、反復ラベル、非数値ラベル変更は一般化しない。数値変更行を別の変更行の根拠に使わない。

32組の数値対応を提案し、写像が成立したのは26実行、そのうち既存の採用条件まで成立したのは24実行（数値変更なしの対照2実行を含む）。残る26実行は採用を見送る。ページを跨ぐ送り帯の元BGR全画素一致は維持する。

以下のUと集約後は**独立診断の候補C/Dに対する件数**。現在の実CLIの件数とは異なる。すべて両方向で成立した。

| 入力 | 候補内訳U → 集約後 | 数値行に残った生差分／内容クラスタ |
|---|---:|---:|
| 末尾 `555→556` | 6 → 2 | 40画素／1件 |
| 中間・物理ページ先頭・文書先頭の変更 | 各6 → 2 | 各40画素／1件 |
| `555→-555` | 7 → 3 | A→Bは326、B→Aは328画素／各2件 |
| `555→55.5` | 6 → 2 | 368画素／1件 |
| `555→1555` | 7 → 3 | 306画素／2件 |
| 同じ行の二つの数値欄 | 7 → 3 | 80画素／2件 |
| 離れた二行の数値変更 | 7 → 3 | 各40画素／1件ずつ |
| 二つの独立原因と途中／末尾の数値変更 | 各11 → 3 | 各40画素／1件 |
| 数値変更なしの対照 | 5 → 1 | 0画素／0件 |

「変更された一行」へクラスタをまとめ直してはいない。符号・桁数・複数欄で二つの内容クラスタになった結果も維持する。

符号変更の生差分画素数は比較方向で2画素異なる。各方向ともPython参照と一致し、内容クラスタ数・集約件数は同じだった。A/B逆転でマスク自体が必ず対称になるとは扱わない。

## 支持の取り違えを防ぐ対照

診断ツールでは、元本文と別に対応IDを作ってC/Dを構築し、採用評価には元本文を戻す。数値が変わった行を「完全一致した支持行」と扱ってはいけないためである。

`weak-actual-support` は、変更行に近い二つの一致行の文字・罫線を両PDFで薄くした入力。対応と写像は成立するが、元本文での採用評価は両方向とも **`insufficient_support / support_ink`** で見送る。同じ画像で、対応IDを元本文扱いした誤った評価だけは支持帯数 `[2,2,2]` で採用される。製品接続ではこの誤採用を拒否する固定回帰を必須とする。

見送った候補Cの数値40画素・1クラスタも保存して監査したが、この未採用Cの6件を製品の件数として扱わない。現製品CLIの同ケースは7件であり、候補の6→6と別の結果である。

最初は文字だけを薄くしたため、罫線が有効な支持として残り、期待した支持不足にならなかった。その結果は `out/t3-1c-numeric/verified/` に保存した。対照の文字と罫線を薄くした最終入力を別フォルダーへ生成し、判定条件や見送り期待は変更していない。最初の通常24ケース48PDFと既存Type3の20PDFは再生成ハッシュが一致する。

## 見送る条件

送り帯自体の数値変更、反復ラベル、非数値ラベル変更、桁区切り、英数字ID、数字だけの行、根拠行不足、行順の入替え、隣接する二行の変更は対応を確定しない。対応が一組できても、別の送り帯の画素／文字が変わった文書は元帯・写像の検証で見送る。挿入を伴わない数値変更も送り・因果集約へ昇格させず、通常の内容差分1件を維持する。

本文・ページの列挙順250条件と、根拠の欠落／重複／位置／文字・選択範囲・上限等630条件の**計880監査条件**が成功した。離れたもう一組が成立して残る20組は監査回数へ加算していない。文書・行メタデータへの監査であり、製品の全設定・資源・保存条件の受け入れではない。

Python側は、元本文と固定期待の一致、数値トークン以外が不変であること、同じページ・一意性・根拠二行・列挙順を照合する。元の完全一致行が跨いだページから独立に成分を構成し、編集列と実構造IDから28原因グループを再構成した。
