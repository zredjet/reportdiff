# PERF-2m PDFテキスト解析の初回負荷とA/B並列化

2026-09-21、開始点`fa28228`。PERF-2lまでの比較コアの改善を維持し、残っていたPDF注釈の初回負荷を調べた。製品の`src/`・設定・判定・配布物は変更せず、コピー上でA/Bの注釈とフォント検査の最大2並列を評価した。

**この段階では製品導入を見送る。** A3の保存までの短縮は約0.6〜1.1%、同一PDFでも約1.7%、自作小PDFはほぼ同速だった。注釈段階の短縮自体は確認できたが、初回の大きな共通負荷が残る。4ページのRSS中央値は約0.10GB増え、観測範囲は重なる。初回フォント検索の補助照合では不一致を観測しなかったものの、製品に新しい並列段階を追加する利益と検証・保守の負担を比べ、現行の逐次処理を維持する。

## 比較した処理

`baseline`は製品のコピー。`pair2`はPDFごとに単語抽出器を持ち、同じページのA/Bを各1workerで処理する。PDFiumの描画と画像比較を終えてから注釈を処理し、注釈の終了後に画像保存、その後にフォント検査を行う。ページ・他段階と重ねず、全ページキャッシュや全画像キューを追加しない。単語抽出器内の上限1を維持する。

両入力がPDFのときだけ分担し、注釈はクラスタがある場合だけ分担する。CPU数1・画像混合・片側ページは逐次。readerは入力側ごとに1個で、同じreaderへの同時アクセスを作らない。注釈とフォント検査は従来の1ページ解析キャッシュを共有する。両側が終わってからA/B順にwriterへ渡し、想定外の例外も両側の終了後にA側から再送出する。

`trace`／`pair2trace`では、PdfPigオープン、ページ解析、単語化、座標変換、クラスタとの対応付け、フォント検査だけに内訳計測を追加した。採否には計測を追加していない通常CLIを使う。候補内探索・特徴量・PNG保存の並列設定は全構成で同じ。

## 依存ライブラリの確認

NuGetのPdfPig 0.1.16に記録されたコミットは[`a7bb356`](https://github.com/UglyToad/PdfPig/tree/a7bb35662bbbf405efddad50aedc9bcdcf515afc)。この版の公式ソース8ファイルを取得し、保存済みソースと全バイト一致を確認した。依存は更新していない。

- `PdfTextReader`のストリーム、document、ページ／フォント警告キャッシュはインスタンスの状態なので、入力ごとに分離する。`PdfDocumentFactory`も既定では呼び出しごとに解析設定やscannerを生成する。
- [単語抽出器](https://github.com/UglyToad/PdfPig/blob/a7bb35662bbbf405efddad50aedc9bcdcf515afc/src/UglyToad.PdfPig.DocumentLayoutAnalysis/WordExtractor/NearestNeighbourWordExtractor.cs)の作業用リストは呼び出し単位だが、optionsを内部で保持する。試作では抽出器も入力別にして、共有する可変設定を追加しない。
- [CMapCache](https://github.com/UglyToad/PdfPig/blob/a7bb35662bbbf405efddad50aedc9bcdcf515afc/src/UglyToad.PdfPig/PdfFonts/Cmap/CMapCache.cs)の外部CMap読み込みには共有ロックがある。Standard14の辞書は静的初期化で構築される。これらの初期化・共有待機は、A/Bを分担しても独立した2倍の処理能力にはならない。
- [SystemFontFinder](https://github.com/UglyToad/PdfPig/blob/a7bb35662bbbf405efddad50aedc9bcdcf515afc/src/UglyToad.PdfPig.Fonts/SystemFonts/SystemFontFinder.cs)にはプロセス共通のフォント・名前・探索済みファイルのキャッシュがある。ConcurrentDictionaryの利用だけを、キャッシュをまたぐ一連の検索や取得したオブジェクト全体のスレッド安全性の証明とは扱わない。

補助プローブでは独立プロセス内のPdfPigキャッシュだけを反復間で消し、`Monaco`の同時検索200回と`Monaco`／`AppleSymbols`の同時検索200回を行った。各組の逐次参照と比べ、不一致は0／400組。OSのフォントファイルは変更していない。これはキャッシュ検索の補助確認であり、多様な未埋め込みPDFやOSでの全体結果の保証ではない。最初に指定した`ArialMT`はこの環境のPdfPigから取得できず停止したため、その試行は成功数に含めていない。

## 検証

製品のReleaseビルドは警告0・エラー0、全1,118件成功。試作を製品へ導入した全回帰の完了とは分けて記録する。

合成PDFは自作Type3、600単語、CropBox、回転、UserUnit、壊れた文字ストリーム、文字／単語上限、本文切り詰め、クラスタなし、先にフォント検査、標準14フォント、埋め込みTrueType、Form／注釈、2ページ目、不正ページ番号、破損PDFの17条件。各構成8反復、計272回で、各readerの逐次参照との注釈・補正／除外・フォント警告・反復キャッシュの一致を確認した。両構成の結果／入力ハッシュも一致した。標準14フォントの字形はOS依存のため、OS間の描画受け入れには数えない。

試作の例外確認ではA/Bを開始した後、Aを失敗させBの終了を明示的に遅らせた。Bが終わる前に全体が戻らず、Bも失敗した後にAの例外が優先されることを確認した。製品用の全入力経路やOOMの受け入れとは別の補助証拠とする。

通常CLIとプローブの全140実行（ウォームアップ込み）で、JSONの生成日時を除く比較内容と全PNGの相対パス・SHA-256が一致した。同一PDF、自作小PDF、画像入力、CPU数1、入力A/Bの逆転を含む。HTML生成は時間に含めるが、HTMLのバイト一致は確認範囲外。プローブは通常CLIとの出力内容も照合した。Coreの製品ソースは全コピーで同じであり、今回100マスクのスナップショット再測定は行っていない。

## 性能測定

## 初回と後続ページ

通常プローブの注釈A/B合計は、単ページで188.14→175.57ms。4ページの1ページ目は191.40→176.40ms、2ページ目は11.50→9.04ms、3ページ目は13.18→11.42ms、4ページ目は2.20→1.63msだった。後続はすでに短いため、並列化で削れる絶対時間も小さい。

単ページの詳細プローブで、逐次のオープンはAが121.31ms、Bが0.46ms。並列ではAが121.23ms、Bが121.21msで、双方がほぼ同じ区間を待っている。ページ解析も逐次49.35／16.42msに対し、並列48.59／48.56msだった。worker内の合計約242msを経過時間や節約可能量と扱わない。

A/Bの入力を逆にしても、逐次の先頭のオープンが115.45ms、後続が0.42msと偏った。先頭入力の内容だけで説明される偏りではない。初回のJIT・静的初期化・共有同期を含む経路の負担が残る観測であり、この内訳だけで各要因の割合までは断定しない。

同一PDFでは文字注釈を省くが、使用フォント検査に解析が必要。通常プローブのフォント段階は186.82→174.63msで、大部分が残った。注釈を省略すれば初回解析も不要になるという設計にはしない。

計測の負担もある。単ページの注釈は詳細なし188.14／175.57ms、詳細あり202.85／182.33ms。詳細プローブの時間は初回／段階の切り分けに使い、通常CLIの改善率として流用していない。

## 確認範囲と次の作業

Windows、低メモリ実機、多様な実帳票、20ページ超・長時間運用は未確認。4／20ページは同じ公開ページの反復で、多様なページで同じキャッシュ効果が得られるとは扱わない。JIT・静的初期化・共有ロック・PDF固有の解析をそれぞれCPUプロファイルで分離した測定ではない。PDF注釈やフォント警告を省く案、解析設定・ライブラリの更新、全ページキャッシュは評価に含めない。

主要段階の並列化はPERF-2lまでで導入済み。次はPERF-2nとして、従来20ページまでだった連続処理を100ページへ延ばし、RSS・マネージドヒープ・GC・ページごとの時間が積み上がるかを確認する。現在の製品を測り、結果一致と時間／メモリの推移を記録する調査を先行する。低メモリPCやWindows実機の受け入れとは分け、単ページの約1%のために新しい並列段階を直ちに追加しない。
