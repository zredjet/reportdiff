# PERF-2i 特徴量の帯サイズ・余白処理の追加調査

2026-09-21。開始点は `c9660c3`。特徴量生成の帯上下で重複する演算を調べ、製品ソースを変更せず比較用コピーで評価した。今回の範囲は試作・出力一致・性能評価と次の実装方針まで。

64行化・インク範囲縮小・Lab行の再利用を組み合わせる試作で、保存までの全体時間は約1.8〜7.2%短縮した。一方、1workerでは約2.6〜4.9%遅くなった。次の導入候補は、現行よりworker数を増やして4workerにできる条件だけでこの組み合わせを使い、それ以外は現行128行を維持する方式。条件切り替え自体は未実装・未測定。

## 比較した処理

現行は128行単位で、インクの背景半径を満たす上下の余白ごとLabに変換する。平滑化・コントラストは必要行だけに限定済みだが、インクの膨張・差分・判定は余白も含む。帯を広くすると重複が減る一方、一時Matの増加で96MiBの予算に収まるworker数が減る。

次の変更を切り分けた。float32の変換式・比較式・しきい値・ページ端の扱いは変えない。

1. 帯の高さを64行または256行へ変更する。worker数は従来と同じ上限4・CPU数・最低2帯・96MiBの予算から選ぶ。
2. インクの計算範囲を中央の必要行へ絞る。余白付きLabからLを取り出し、その中央ROIを膨張する。背景からLを引く処理を同じ一時Matへ書き戻し、判定は最終インクの担当行へ直接書く。L・背景Matは帯の末尾で解放し、次のLab変換まで保持しない。
3. 同じworker内で、次の帯にも必要なLab行を再利用する。固定バッファ内の重複部分を移し、新しい入力行だけを変換する。worker間でバッファを共有しない。

再利用では、有効な行数だけを持つMatヘッダーをバッファ上に作る。単に固定バッファのROIを渡すと、最終帯の後ろに残った古い行をフィルターがページ外の近傍として参照しかねないためである。ヘッダーはバッファを所有せず、各帯のヘッダーを先に、workerのバッファを最後に破棄する。重なる行の移動は `Span.CopyTo` を使う。

| 構成 | 帯の高さ | インク範囲縮小 | Lab再利用 |
|---|---:|---|---|
| 現行 | 128 | なし | なし |
| `stripe64` / `stripe256` | 64 / 256 | なし | なし |
| `ink128` / `ink64` | 128 / 64 | あり | なし |
| `reuse128` | 128 | なし | あり |
| `combined128` / `combined64` / `combined256` | 128 / 64 / 256 | あり | あり |

## 画素値と予算

現行と8試作の各構成で314照合が成功した。37ゴールデンのA/B、幅1、64/128/256行の前後、末尾1行、非連続ROI、300/400dpi、通常／厳密、インク有無、背景半径0.001/1.5/20mm、1/2/4/8workerと予算不足時の逐次復帰を含む。全ページ演算と、特徴量・コントラスト・インクをバイト単位で比較し、親画像も不変だった。

一時Matの見積もりは、帯の高さを `S`、余白付き高さを `L`、幅を `W` とすると、現行のインクあり通常比較が `W × (12S + 25L)` bytes。インク範囲縮小では `W × (12S + 24L)` とした。Lab変換中のfloat3画像2枚が24Lで、その時点で前の帯のL・背景画像を解放している。インク計算中のLab・L・背景は `16L + 4S ≤ 24L` に収まる。厳密比較では収縮用の12Sが不要。実際の高さはページ高で切り詰める。

Lab再利用の固定バッファもこの見積もりに含める。入力・最終特徴量・ネイティブ内部の作業領域・アロケータ保持分は含めず、RSSの上限ではない。1worker分も予算に入らない条件は従来どおり逐次へ戻る。

## 特徴量生成だけの補助測定

Apple M4 Max（16コア・128GiB）、macOS 26.5.1、.NET 10.0.12 / SDK 10.0.401、Release。公開A3工程表の保存済みA画像から、1画像分の特徴量生成を測った。各構成・各DPIは独立プロセス、3回ウォームアップ後7回の中央値。生成結果のSHA-256は構成間でも一致。PNG読み込み・ハッシュ検査・解放を時間に含めず、強制GCはしない。

| Lab再利用・128行 | 49.12ms | 3 | 79.98MiB | 146.52ms | 2 | 74.88MiB |

帯を広げるだけでは、重複削減よりworker数の減少の影響が大きかった。64行では4workerが予算に収まり、特に現行2workerの400dpiで改善が大きい。Lab再利用だけの128行は一貫した改善にならず、他の変更との組み合わせで評価する。

ソースと実際のworker数から計算すると、300dpiの1画像のLab変換対象行数は、現行4,480行、64行のみ5,452行に対して、再利用あり64行は3,616行になる。400dpiも現行6,405行、64行のみ8,162行に対して4,821行。画像高はそれぞれ3,508／4,677行。64行で増える余白の重複を、worker境界に必要な分だけへ減らしている。これは処理範囲の計算値で、CPU時間やメモリ帯域の実測値ではない。

## 逐次・設定違い・検証のまとめ

同じ保存済み画像を使い、特徴量生成単体で追加条件を測った。各構成3回ウォームアップ後7回、生成結果のSHA-256は一致した。CPU数1は `DOTNET_PROCESSOR_COUNT=1` によって.NETが認識するCPU数を変えた補助測定で、物理的な1コア実機ではない。

| 条件 | 現行 | 64行のみ | インク範囲縮小64行 | 両方64行 |
|---|---:|---:|---:|---:|
| 300dpi・1worker | 135.76ms | 153.22ms | 142.72ms | 142.43ms |
| 400dpi・1worker | 277.86ms | 323.05ms | 290.01ms | 285.18ms |
| 300dpi・エッジ許容0・インクあり | 25.51ms | 29.90ms | 29.73ms | 24.40ms |
| 400dpi・エッジ許容0・インクあり | 62.77ms | 64.27ms | 57.35ms | 51.10ms |
| 300dpi・通常・インクなし | 27.91ms | 28.38ms | 27.41ms | 27.46ms |
| 300dpi・背景半径20mm | 2,653.49ms | 4,616.79ms | 2,593.70ms | 2,559.16ms |

1workerでは組み合わせ案も約2.6〜4.9%遅くなり、64行を無条件に採用する根拠にはならない。インクありのエッジ許容0では、300dpiは現行・試作とも4worker、400dpiは3→4workerだった。インクなしは両方4workerで、追加効果は小さい。背景半径20mmでは全構成1workerに制限され、帯の高さだけを半分にする案は大きく遅くなった。

通常CLIの66実行と段階計測32実行、計98実行（ウォームアップ込み）で、JSONの `schema_version/tool/inputs/config/summary/warnings/pages` と全PNGの相対パス・SHA-256が一致した。生成日時は比較対象外。HTML生成は時間に含めるが、バイト一致・ブラウザの再確認は対象外。

現行・64行のみ・インク範囲縮小64行・両方64行の4構成で、各100条件の比較結果スナップショットも完全一致した。内訳は37ゴールデン、60の画像端・ROI・設定等、3つの大画像。特徴量の全ページ参照との照合は9構成×314件＝2,826件、特徴量単体の通常180反復と追加条件240反復も構成間でハッシュが一致した。

製品側のReleaseビルドは警告0・エラー0、全1,023件のテストが成功した。最終ビルドの製品DLLと測定に使った現行DLLも一致した。保存したコピー生成ツールから全8試作を再生成し、計測済みコピーのC#ソース・プロジェクトと一致することを確認した。試作DLLに対する全1,023件の実行、例外注入による解放の確認は今回の範囲に含めず、製品導入時に実施する。

## 次の実装で守る条件

次の実装候補は、**現行128行よりworker数を増やして4workerにできる条件で、64行化・インク範囲縮小・worker内Lab再利用を一組として使う方式**。それ以外は現行128行の処理へ戻し、観測した逐次の悪化を避ける。今回の通常300/400dpiとインクあり・エッジ許容0の400dpiは対象になる。すでに4workerの条件、CPU数1〜3、予算不足、小画像は最初の導入対象を広げない。

この条件切り替え自体はまだ実装・測定していない。製品への適用は次のタスクとし、今回のコピーの成功を製品実装の受け入れに含めない。異なる幅や予算での切り替え境界も次工程で確認する。

- 全ページ演算を基準に、float32特徴量・コントラスト・インクのバイト一致を維持する。帯・worker境界、末尾の短い帯、画像端、幅1、ROI、大きな背景半径、インクなし・厳密比較を回帰に含める。
- 画像ごとに現行128行と候補64行のworker数・予算を比較して選択する。選択した帯の高さをスケジュールと走査へ明示的に渡し、グローバルな帯サイズを書き換えない。96MiB・最大4worker・予算不足時の逐次復帰を維持する。既存の帯数・予算テストを更新する際も、独立した全ページ演算の基準は変えない。
- 再利用の対象は同じ画像・同じworker内のLab行だけ。所有するバッファと借用ヘッダーの寿命、失敗時の全worker終了待ち、部分生成した特徴量の破棄を検証する。次の帯へ進む前に前のヘッダーを破棄し、無効な残り行を参照しない。
- 比較式・探索順・しきい値・公開設定・PNG並列化等の他段階は変更しない。全回帰、比較結果のスナップショット、CLIのJSON/PNG一致、時間・RSSを最終製品で再測定する。
- Windows、低メモリ実機、物理的に少ないCPUコア、多様な帳票、20ページを超える処理・長時間運用の未確認範囲を維持する。
